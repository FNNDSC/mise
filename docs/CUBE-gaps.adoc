= CUBE Gaps Exposed by mise
:toc:
:toclevels: 3

== What this is

A record of places where a normal operation costs a client more than it should, and what CUBE could offer instead. Each entry states the operator requirement, the burden the gap currently imposes, and the Collection+JSON interface that would remove it.

Filing here is an obligation, not a courtesy. `mise` may work around a CUBE weakness; it may never do so silently (see link:principles.adoc#no-silent-workaround[no silent workaround]). A compensation nobody records is a gap nobody funds, and every later client inherits the same trick without knowing why it exists.

Nothing here proposes a non-C-J endpoint. A proposal is a *read projection* or a repair to an existing collection. CUBE remains authoritative for users, groups, feeds, plugin instances, files, and permissions; a projection answers a bounded question about that state and never becomes a second source of truth. The criteria a proposal must meet are in <<criteria>>; the shape every entry follows is requirement, burden, interface, client policy.

== Confirmed proposal: group memberships

Upstream: https://github.com/FNNDSC/ChRIS_ultron_backEnd/issues/730[ChRIS_ultron_backEnd#730].

=== Operator requirement

A permitted client needs a bounded snapshot of the groups and memberships visible to its authenticated CUBE identity. It needs this for `/etc/group`, group administration views, and any surface that presents group membership as a relation rather than asking only about one known group.

This is not a requirement for CUBE to persist a group file.

=== Proposed C-J collection

Prefer a flat relation collection:

----
GET /api/v1/group-memberships/?limit=100&offset=0
----

Each C-J item represents one canonical group/user membership relation and carries the projection fields needed to render or group it locally:

----
{
  "data": [
    { "name": "id", "value": 91 },
    { "name": "group_id", "value": 7 },
    { "name": "group_name", "value": "pacs_users" },
    { "name": "user_id", "value": 12 },
    { "name": "username", "value": "peter.hong" }
  ],
  "links": [
    { "rel": "group", "href": "…/groups/7/" },
    { "rel": "user", "href": "…/users/12/" }
  ]
}
----

Groups with no memberships still need representation. The same read interface can provide those as ordinary group collection items through an embedded/expanded `members` relation, or CUBE can define the collection contract to include a separate group summary section/link. This is an open interface question; it must be settled before implementation so clients do not infer empty groups from absence.

The existing group and group-user mutation collections remain canonical for writes. `group-memberships` is read-only.

=== Required interface semantics

* The collection applies CUBE's normal authorization rules. It must never reveal a user or membership the requesting identity could not otherwise inspect.
* It is paginated and returns the normal C-J total/next relation. ChELL must not assume all memberships arrive in one response.
* Its response is a snapshot. CUBE may expose an HTTP `ETag` or a revision fact so clients can revalidate cheaply.
* CUBE performs the join/prefetch internally. A caller does not discover per-group member URLs and replay the join itself.
* Exact group or username filters may be added only where they preserve the same collection semantics and have a demonstrated caller.

=== ChELL cache policy after CUBE support

ChELL still keeps an identity-scoped snapshot because `/etc/group` is read often and changes comparatively rarely:

* key: normalized CUBE URL plus authenticated username;
* freshness: five minutes unless CUBE supplies a cheaper validator;
* ChELL-originated membership mutation: invalidate immediately; and
* outside mutation: visible after revalidation/expiry.

The difference is that a cold snapshot becomes one paginated collection traversal, rather than N per-group membership traversals.

== Confirmed proposal: administrator identity directory

Upstream: https://github.com/FNNDSC/ChRIS_ultron_backEnd/issues/727[ChRIS_ultron_backEnd#727].

=== Operator requirement

An ordinary operator needs only the identity under which their ChELL session is connected. An elevated CUBE administrator also needs a complete, paginated directory of the CUBE identities that CUBE regards as administrable, including federated identities synchronized into CUBE. This supports account administration, group membership selection, and a familiar administrative inspection:

[source,bash]
----
cat /etc/passwd        # session operator only
sudo cat /etc/passwd   # identities visible to the temporary CUBE administrator
----

This is an identity projection, not a password database. It must never expose password hashes, bearer tokens, or external identity-provider credentials.

=== Existing C-J seam and its defect

No new endpoint shape is needed. CUBE already publishes the ordinary C-J collection URL:

----
GET /api/v1/users/?limit=100&offset=0
----

The present implementation declares `User.objects.all()` but calls the list renderer with an empty list, so every collection response is empty. Separately, the current object permission permits a safe read of any known user detail to every authenticated caller. This is neither a useful administrative collection nor a coherent least-disclosure policy.

=== Required interface semantics

Repair the existing `users` collection rather than adding an administration-specific or shell-specific variant:

* An authenticated non-administrator cannot enumerate the collection. It receives a normal authorization failure; its own identity remains available through CUBE's existing authenticated-user link/resource.
* An authenticated CUBE administrator receives every CUBE user visible to that CUBE, including synchronized federated identities, through normal pagination.
* A user-detail read is available to its owner and to an administrator. If a future caller needs a deliberately public identity card, that must be a separate minimal projection with an explicit disclosure policy, not an accidental consequence of the account-detail serializer.
* Each C-J item supplies at least stable `id`, `username`, and any approved display/contact field needed by legitimate administration. Password fields, hashes, tokens, and provider credentials are never C-J item data.
* Exact username filtering may be added for administrator workflows, provided it preserves the same authorization, pagination, and C-J semantics.

This is a small, deep interface: CUBE owns user storage, federation synchronization, authorization, filtering, and pagination behind one existing collection seam. Clients no longer infer an account directory by probing numeric IDs or by reimplementing CUBE's authorization rules.

=== ChELL projection policy after CUBE support

Without `sudo`, `/etc/passwd` remains one record obtained from the authenticated-user resource; it does not trigger a directory traversal. Within `sudo`, ChELL traverses the repaired `users` collection using the temporary elevated CUBE client and renders its approved fields as POSIX-style records.

The elevated listing must not populate a cache keyed only by the normal session identity. ChELL should either render it without caching or key any short-lived cache by the effective elevated identity and invalidate it when the elevation scope ends. An administrator's visibility must never become ambient output for the original operator after `sudo` returns.

== Candidate proposal process for `/proc`

Do not create a CUBE `/proc` endpoint. `/proc` is ChELL's VFS projection. First determine whether the ordinary C-J feed and plugin-instance collections lack a query shape needed by several clients.

If they do, prefer one of these C-J-native evolutions:

* a compact, visible-run index collection with feed identity and aggregate counters; or
* a bounded plugin-instance collection representation that can return the minimal topology fields for a selected visible run or query scope.

Avoid a universal, unbounded graph-document endpoint. It would couple clients to a large mutable representation, complicate authorization, and merely move ChELL's current global sweep into a less inspectable server response.

The required evidence is a trace showing the current request sequence, visible scope, response sizes, cold/warm latency, and which fields force the follow-up requests.

== Confirmed contract-integrity gap: plugin execution schemas

Upstream: https://github.com/FNNDSC/ChRIS_ultron_backEnd/issues/729[ChRIS_ultron_backEnd#729].

=== Observed failure

For a versioned plugin executable, ChELL's ``--parameters`` view reads the
ordinary C-J relation:

----
GET /api/v1/plugins/{plugin_id}/parameters/
----

That collection is not a ChELL approximation. In CUBE it is the plugin's
``parameters`` relation, and its items are the parameter records used when
CUBE validates and creates plugin instances. It is therefore the authoritative
*registered execution schema* for that CUBE plugin version.

On the observed production CUBE, ``pl-pfdo_med2img v1.2.2`` returns ten such
records even with an explicit high collection limit. The source at the exact
``1.2.2`` tag declares twenty-four plugin flags through
``ChrisApp.add_argument``; fourteen are absent from CUBE. The ten returned
records are the first ten source declarations in order. This is not pagination,
renderer filtering, or a README-only discrepancy: the historical registration
manifest is incomplete or was not refreshed from the image.

=== Boundary and requirement

A README is prose and may document an upstream module, historical options, or
container-internal switches. It must not be parsed by ChELL into a runnable
schema. The plugin's machine-readable ``ChrisApp`` declaration is different:
it is the input used to form a registration manifest. A registration whose
parameter collection omits those flags makes CUBE's own canonical execution
schema incomplete: users cannot reliably discover or set the supported run
contract.

The required CUBE contract is:

* for each immutable plugin name/version/image registration, the
  ``parameters`` C-J collection is the complete set of CUBE-supported runtime
  flags, including type, flag spelling, default, requiredness, help, and
  whether a parameter is UI-exposed;
* the registration pipeline validates that declared manifest against the
  image's machine-readable CLI declaration where the plugin supplies one;
* CUBE records provenance for that manifest: at minimum the image digest (or
  immutable image reference), declaration source, and validation/registration
  timestamp; and
* a mismatch is a registration/CI failure or an explicitly marked exception,
  never something clients silently reconcile from README text.

The existing ``/plugins/{id}/parameters/`` collection remains the right C-J
read seam; no shell-specific endpoint is needed. Provenance can be supplied
as approved data on the existing plugin item or a normal linked C-J manifest
item if clients need to inspect it. The immediate production repair is to
correct the registered parameter manifest for the affected plugin version
without making the README a second source of truth. Before changing production
data, capture the registration payload produced from that image and compare it
with CUBE's resulting C-J collection. This distinguishes an incomplete
historical registration from a truncation fault in the registration pipeline.

=== ChELL policy

``plugin-vX --parameters`` means “CUBE-declared run parameters,” not every
option mentioned in documentation. ChELL should label that boundary plainly.
``--readme`` remains the human documentation view. Once CUBE supplies
provenance or a verified manifest state, ChELL may show it, but it must not
invent an executable parameter from README prose.

== Confirmed proposal: directory archive

Issue #233. Upstream research ticket: https://github.com/FNNDSC/ChRIS_ultron_backEnd/issues/731[ChRIS_ultron_backEnd#731] (streaming archive vs utility feeds; see the note at the end of this section).

=== Operator requirement

Take a copy of a directory. A feed's output, a series pulled from PACS, a plugin's working set — the everyday act of getting a tree of files out of CUBE and onto the machine a person is sitting at.

[source,bash]
----
download /home/me/feed_123/pl-dcm2niix_45/data ~/scans
----

A single file is straightforward: CUBE serves its bytes. A *directory* has no representation CUBE can hand over, and that absence is the gap.

=== The burden today

There is no directory-archive route, so a client must build the archive out of the platform's own parts. The established workaround — arrived at independently in the ChRIS web UI years before `mise` — is to run one:

. create a feed;
. attach `pl-dircopy` rooted at the directory being copied;
. attach a zip plugin downstream of it;
. poll until the job completes; and
. serve the resulting archive as an ordinary file.

Using a plugin for the archiving itself is correct. "Make an archive" is a computation, and on this platform computations are plugins; inventing a separate zip service would be the erosion this document exists to prevent. The problem is everything around it.

*The orchestration has no home.* Feed creation, plugin attachment and completion polling are a workflow, and CUBE offers no way to express it as one thing. So every client re-implements it, and the sequence exists only as a series of REST calls inside somebody's source. In the web UI this is precisely how a presentation layer became an orchestrator — the point at which business logic and rendering co-mingled in a client no other client could reuse. `mise` at least confines it to the intent kernel, where every surface reaches the same implementation, but it is still a workflow standing in for a missing route.

*It pollutes provenance.* A download creates a feed. The compute DAG — the record of which plugin instance produced which artifact — acquires an entry asserting that someone took a copy, as though that were an analysis step. A user's feed list fills with archive jobs, and the graph that exists to answer "how was this derived" now answers a question nobody asked.

*It is slow and failure-prone out of proportion to the request.* Copying a directory should not require scheduling compute, waiting on a job queue, or recovering from a plugin that failed halfway. The latency is that of a pipeline run rather than of a read.

*It leaves an artifact nobody asked for.* The archive persists in CUBE storage after the person has their copy, and no client currently owns cleaning it up.

=== Proposed interface

An archive representation of an existing directory, requested through the ordinary collection graph rather than by scheduling compute:

----
GET /api/v1/filebrowser/<path>/archive/?format=zip
----

The precise shape is CUBE's to choose — a link relation on the existing filebrowser collection item is the natural seam, since that collection already represents a directory and already knows its contents and the caller's permission to see them. What matters is that a directory acquires a fetchable representation.

Required semantics:

* it applies CUBE's normal authorization, and never includes a file the caller could not fetch individually;
* it streams, so a large tree does not require CUBE to materialize the whole archive before responding;
* it creates no feed, no plugin instance and no durable artifact — a read leaves the compute graph untouched;
* it bounds or reports its size, so a client can refuse or warn before starting; and
* it names its format explicitly rather than implying one.

=== Why an existing collection is insufficient

The filebrowser collection already enumerates a directory's contents, so a client can fetch every file and assemble an archive locally. That is the same N+1 traversal this document objects to elsewhere, with the added cost that a browser must hold the whole tree in memory to build a zip it then hands to the download manager.

The plugin route is not an interface. It is a client compensating for a missing one, and it is filed here because it works well enough to be invisible — which is exactly the condition under which a gap stops being felt and never gets fixed.

The narrower statement, settled 2026-09-03: the gap is that a directory has no *read* representation and that there is no non-provenance way to run utility compute. Two CUBE answers are plausible and may both be right — a streaming archive for trees under a size bound, and utility (ephemeral, provenance-hidden, auto-reaped) feeds that keep the plugin route for large trees. Which, and where the bound sits, is the research question in ChRIS_ultron_backEnd#731.

=== Client policy until then

`mise` walks the directory and fetches each file individually — `files_listRecursive` plus one request per file. That is the N+1 traversal this document objects to elsewhere, chosen because it needs no compute and leaves the compute graph clean, and acceptable only because a local shell writes the files as they arrive.

It does not survive a surface with no filesystem. A browser cannot receive several hundred files as several hundred saves, so `mise` adopts the archive workflow — `pl-dircopy` into a zip plugin — for exactly that case. It lives in `brasa`, not in a surface: the orchestration is an intent, so every surface reaches one implementation and no client re-derives the sequence, which is the failure the web UI ran into. The resulting archive is a CUBE artifact with an ordinary path, delivered through the surface capability like any other file (issue #232), so no daemon filesystem is involved.

The workaround announces itself rather than running silently: a directory download reports that it is creating a feed in order to do so, and says why.

== Confirmed proposal: server version identification

Upstream: https://github.com/FNNDSC/ChRIS_ultron_backEnd/issues/728[ChRIS_ultron_backEnd#728].

=== Operator requirement

A client cannot ask a CUBE what version it is. Neither the unauthenticated nor the authenticated API root reports a server version, no response header carries one, and no dedicated endpoint exists. A client that must interoperate across CUBE versions is therefore reduced to behavioral fingerprinting: attempting a request in the current dialect and interpreting the failure.

This stopped being hypothetical on 2026-08-25. The `userfiles` rename field drifted from `path` to `upload_path` between the CUBE version deployed at BCH and the one at cube.chrisproject.org, which silently broke every mise file move against current servers until a typed-API test tripped over it. The client-side remedy, send the current field and fall back to the legacy one on rejection, works but is exactly the kind of guess-and-retry that version negotiation exists to prevent, and it costs a failed round trip per affected call on older servers. Each future wire drift will force another such probe pair unless the server can simply be asked.

=== Proposed interface

A single unauthenticated read, stable across versions from its introduction onward:

[source,console]
----
GET /api/v1/version/
----

returning at minimum the CUBE semantic version, and ideally the versions of the co-deployed services a client may speak to through CUBE's mediation (pfcon, pfdcm) where CUBE knows them. Unauthenticated because version discovery must precede login: a client that adapts its dialect needs the answer before it sends its first mutating request. An `Accept: application/json` body of the shape `{ "version": "6.11.0" }` suffices; a C-J rendering may accompany it for uniformity.

=== Why an existing collection is insufficient

The API root was probed on both reference deployments: the authenticated root returns a plain paginated collection with no version-bearing field, link, or header, and nothing else in the collection graph carries deployment identity. There is no existing seam to expand; absence is the defect.

=== Client policy until then

mise carries dialect fallbacks where drift is known (currently the `userfiles` rename field) and treats any newly discovered drift the same way: current dialect first, legacy on rejection, with the drift recorded in the relevant module and guarded by the live nightly against a current-version CUBE. These fallbacks are removable the day a version endpoint exists.

== Confirmed gap: a shared feed grants its listing but not its contents

Upstream: not yet filed. The evidence below was captured 2026-09-04 against a production CUBE.

=== Operator requirement

A feed shared with an identity is shared so that identity can look at what it holds. An operator who can see a result file, its name and its size, expects to be able to read it. That is what sharing means to the person doing it.

=== Observed behaviour

A feed owned by another user and shared with the operator lists normally. The operator's client walks `/proc/jobs/feed_<id>/<node>/data`, receives one entry, and is told its size is 49,346 bytes. Reading it fails.

Asked directly, CUBE is unambiguous. `GET /api/v1/userfiles/<id>/` for that file returns *403 Forbidden* for the same authenticated identity that just listed it. It is not a 404: the file exists and CUBE knows the operator is asking about it. The same request shape against a file in the operator's own space returns the content.

So visibility and readability disagree. The share propagates to the folder tree and to file metadata, and stops before the bytes.

=== Why this is a gap and not a client defect

The client cannot compensate. There is no interface that reports, per file or per feed, which entries the identity may actually read, so a browser cannot mark them ahead of a click; it can only be refused and remember. Nor can it fetch the file another way: the refusal is CUBE's, on the canonical resource.

It also cannot be inferred from the feed. The operator is a legitimate viewer of the feed — the roster returns it, the topology loads, the job statuses read. Only the file payloads are withheld.

=== What CUBE could offer

Either behaviour would remove the gap; they are alternatives, not a sequence.

* *Make the share cover the contents.* If a shared feed's files are meant to be readable, the file resources should honour the same permission the listing already does. This is the interpretation an operator expects, and it needs no new interface.
* *Make the boundary legible.* If withholding contents is deliberate — a plausible policy, since a feed's outputs may carry data the sharer did not intend to hand over — then a listing must say so. A per-entry readability fact in the filebrowser response, or a documented rule stating which classes of file a share does and does not convey, lets a client render the truth instead of discovering it one refusal at a time.

The present behaviour is the worst of the two: it offers the file, then refuses it, and says nothing about which files will behave that way.

=== Client policy until then

`mise` treats a refusal as an answer rather than an absence.

* The failure path asks CUBE for the real status and reports it, rather than the previous "not found (404) or access denied (403)" — two opposite answers in one sentence, and neither of them measured.
* A refused read renders as a refusal, with CUBE's reason, never as empty content. An empty pane where a file should be is indistinguishable from an empty file.
* The path is remembered for the session and the row is marked unreadable, so an operator learns each boundary once rather than every time the listing is redrawn.

None of that narrows the gap. It only stops the client from lying about it.

[[confirmed-gap-pacs-query-collection]]
== Confirmed gap: the PACS query collection cannot be searched by its query, and every row carries its result

=== Operator requirement

A client that has just been asked a PACS question wants to know whether that exact question has already been answered, because the stored answer is instant where the PACS is not. CUBE keeps every answer — 1,817 of them on the CUBE measured — so the data is there. The collection simply cannot be asked the one question a client needs to ask of it.

=== Measured

Against a live CUBE on 2026-09-05, `GET /api/v1/pacs/queries/`:

[source]
----
total: 1817
row fields: id, creation_date, title, query, description, status,
            pacs_identifier, owner_username, execute, result
searchable: id, min_creation_date, max_creation_date, title_exact, title,
            status, execute, description, pacs_id, pacs_identifier,
            owner_username
----

Two things follow. `query` — the criteria, the field that identifies what a stored query asked — is a row field and not a search parameter, so a client cannot ask CUBE which query had given criteria. And `result` — the zlib+base64 pfdcm payload, 2 KB and 21 KB in the two rows sampled — rides every row of every list response, whether or not the client wants it.

Together these make the only available strategy the worst one: to find whether a question was asked, a client must page the whole collection, and each page carries payloads it will discard. On the measured CUBE that is roughly 15 MB across 19 requests to answer one lookup. Worse, a *miss* — the common case for a genuinely new query — always costs the full sweep, so a client that searched naively would make every new query slower than not searching at all.

mise works around this with a local index built from a deferred background sweep (see epic #379), which pays the cost once instead of per query. The workaround is sound but it exists only because the collection cannot answer directly, and every other client faces the same wall.

=== Required interface semantics

Either of these resolves it; both together would be better.

* *A search parameter over the stored criteria.* Exact match on the serialized `query` would be enough for the identity case; a contains-style match would additionally serve "what have I asked about this patient".
* *Field projection on list responses.* A `fields=` parameter, or simply omitting `result` from list responses and serving it only on the detail route. `result` is the largest field in the collection by a wide margin and is almost never wanted when listing. This alone would turn a sweep from megabytes into kilobytes and would help every client that lists queries, not only one that searches them.

The second is the more valuable of the two and the cheaper to provide. A client listing 1,817 queries to show the operator their history — which mise's `/net/pacs/queries` does — is today paying for 1,817 decoded-on-demand payloads it will never open.

=== ChELL policy after CUBE support

The index in #379 becomes an optimisation rather than a necessity, and the deferred sweep that fills it can be dropped or reduced to a cheap projection query. The advisory contract stays either way: a hit is confirmed by decoding before it is served.

[[candidate-proposal-change-discovery]]
== Candidate proposal: change discovery

Upstream: https://github.com/FNNDSC/ChRIS_ultron_backEnd/issues/644[ChRIS_ultron_backEnd#644].

This entry is a candidate, not a confirmed proposal. It does not yet carry the captured trace and representative timing that <<adding-an-entry,Adding an entry>> requires, and it must not be implemented against until it does. It is recorded now because the compensation is already in the client and an unrecorded compensation is a gap nobody funds.

=== Operator requirement

A client needs to know *that* a resource it holds has changed, without asking every resource whether it changed. The operator-visible cases are ordinary: a job the operator launched finishes and writes output while the client is away; a colleague shares a feed; an administrator registers a plugin. In each, something the operator can already see in another CUBE client is invisible in this one until a timer happens to fire.

This is not a requirement for CUBE to deliver events to a listener. It is a requirement to be able to *ask what changed*.

=== The burden today

CUBE offers no way to ask. Every client that wants to stay current re-reads collections it already holds, on a clock it invents, and compares.

In `mise` that clock appears at least three times, none of them related to when anything actually changed:

* the `/proc` roster full walk, at most once per `ROSTER_FULL_WALK_MS` (ten minutes), which is the only mechanism by which a feed shared to this identity after the client's highest known feed id is ever discovered — a boot delta filters on `min_id` and cannot see it;
* a settled feed's row re-check, at most once per `FEED_RECHECK_MS` (ten minutes); and
* the directory-listing cache's per-path expiry, three minutes by default, which re-fetches a listing whether or not the underlying folder moved.

The costs compound with feed size. A full roster walk pages the feed collection at one hundred rows per request. A single large feed's plugin-instance topology is measured at roughly two and a half seconds per hundred-row page, so a feed of eighty-eight thousand nodes costs the better part of an hour to index, and any recheck that cannot be scoped to what changed pays that again.

The operator-facing consequence is the one worth stating plainly: a feed shared to this identity is silent until a full walk happens to run.

=== Proposed interface

Two proposals, deliberately separable. The first is small and immediately useful; the second is the architecture the upstream issue is asking about. The first does not depend on the second and should not wait for it.

*Near-term: a modification filter on existing collections.* A `modified_since` query parameter on the feeds collection, and on the plugin-instances collection, returning the ordinary C-J collection filtered to items whose server-side modification fact is newer than the supplied instant. This turns a client's periodic full walk into a bounded question and removes most of the polling cost with no new resource, no new transport, and no change to what is authoritative. A companion `shared_since` semantic, or the inclusion of share events in the same modification fact, is required for the shared-feed case, since sharing a feed to an identity may not alter the feed row itself.

*Longer-term: a change collection with a resume cursor.* An ordinary paginated C-J collection whose items are change records, each carrying a monotonic id, the changed resource's canonical URI, and a change kind. A client asks for records after the cursor it last saw:

----
GET /api/v1/changes/?after=<cursor>&limit=100
----

Three properties matter, and they are what distinguish this from an event bus:

* *Records are thin.* An item names a URI that changed and says nothing about what it changed to. The client refetches the canonical resource. A record carrying state would become a second source of truth that can disagree with the first, which this document forbids.
* *There is no subscription.* Nothing is delivered, so nothing is missed when a client is not running. A client absent for a week resumes from its stored cursor and reads the backlog.
* *Retention failure degrades to today.* If a cursor is older than the server's retention window, CUBE says so explicitly and the client falls back to the full walk it performs now. The degraded path is the current behavior, not a new failure mode.

Real-time push, if it is ever wanted, belongs on top of this and never in place of it: a transport that says only "records exist after your cursor", after which the client reads the collection. The log stays authoritative; a client that misses every notification is slower, never wrong.

=== Why an existing collection is insufficient

The feeds and plugin-instances collections are authoritative for state and answer none of these questions. They expose no server-side modification fact a client may filter on, so "what changed" is only answerable by reading everything and diffing locally, which is the burden above. Neither is there any representation of a share becoming visible to an identity, which is why a shared feed cannot be discovered by an id-ordered delta at all.

An HTTP validator such as `ETag` on a collection would help a client skip an unchanged page, but not find a changed item among many pages, and not at all for the shared-feed case.

=== Client policy until then

`mise` keeps its own polling and states its cost rather than hiding it:

* the `/proc` roster and per-feed rechecks remain on their timers, and remain the sole source of truth about what changed;
* the directory-listing cache stops keeping an independent clock for anything `/proc` reports on, and is invalidated from the roster and job-completion facts instead — one poller of record rather than several uncoordinated timers; and
* paths no CUBE poller reports on, such as `/bin`, `/etc/group` and the PACS trees, keep a plain expiry, because guessing is all that is available for them.

That policy narrows the gap's blast radius. It does not close it: the freshness of every signal-covered path is still bounded below by the roster walk's period, and no client-side arrangement can improve on that.

== Appendix: what qualifies

=== When client work is a CUBE gap

A cache is not evidence of a backend defect. Completion indexes, renderer state, and a session's recent navigation are legitimate client working-set state.

A gap is indicated when all of the following hold:

. a normal operator action needs a cross-resource aggregate;
. the client must fan out into N requests, or otherwise reconstruct a relation CUBE already owns;
. the resulting projection would also serve another legitimate CUBE client, such as the web UI or an administrative surface; and
. the cost is measured on a representative CUBE and exceeds the interaction budget.

The response is a small, deep collection interface that hides joins, authorization filtering and pagination inside CUBE — never making a client's local cache authoritative.

=== What a projection must declare

* its authoritative CUBE facts;
* its authorization and visibility scope;
* pagination and result bounds;
* snapshot and freshness semantics; and
* the stable fields clients may rely on.

A projection is a snapshot, not truth. `/etc/group` is a POSIX-shaped view over CUBE group and membership relations, useful because membership changes less often than it is read. It is not the group model.

=== Still C-J

A new read model is an ordinary CUBE collection: a collection URL with normal pagination and link relations, C-J item `data` for projection fields, links to the canonical resources where useful, and normal HTTP validators such as `ETag` where CUBE can provide them.

Not RPC-shaped `getGroupFile` calls, not shell-specific text endpoints, not a parallel transport. `mise` renders C-J data into its POSIX views; CUBE does not need to know that a consumer calls one view `/etc/group`.

== Appendix: examined and not proposed

Client caches that were measured against the criteria above and judged normal working-set state. Recorded so the same ground is not re-argued, and so a later measurement can promote one.

[cols="1,2,2",options="header"]
|===
| Client work | Judgment | What would change it

| `/bin` tool and pipeline index
| Normal session working-set cache. The data is already collection-shaped and the warm-up is not known to reconstruct an N+1 relation.
| A measured cold latency or pagination cost that exceeds the interaction budget.

| CFS feed and public-path listings
| Normal path/list cache, with one part promoted. Its *shape* is still ordinary working-set state; its *freshness* is not, because no CUBE interface lets a client ask what changed. See <<candidate-proposal-change-discovery,change discovery>>.
| A measured path listing that itself fans out through several CUBE resource collections.

| `/proc` feed index
| Candidate. A run dashboard, a shell, and the argus surface may all want a compact visible-run index, but the existing C-J feeds collection may already satisfy it.
| Query count, payload, cold latency, and the fields unavailable without follow-up requests.

| `/proc` topology index
| Strong candidate, not a conclusion. The client may legitimately own its navigation index; CUBE may need only a more selective collection query rather than a new topology object.
| Sweep cost, plus the minimum shared projection: node identity, feed identity, parent/previous relation, plugin identity, status counters.

| `StudyDescription` as a PACS query key
| Not a CUBE gap. `pacs query` whitelists nothing, so the key reaches pfdcm and the PACS; measured against a live PACS (PACSDCM, 2026-09-05), `PatientID:<id>,StudyDescription:CT-Outside Images on PACS` returned the same two studies as `PatientID:<id>` alone, including the XR study that does not match. The key is an *optional* C-FIND matching key in the DICOM standard, so a PACS is within its rights to ignore it. Recorded so a surface does not offer a query field that silently does nothing: argus shows STUDY as a listing column but not as a query term.
| A PACS that honours it, or a pfdcm interface that reports which keys a server actually matched on — the second would be worth asking for, since a client cannot otherwise tell a narrowed result from an ignored key.
|===

== Adding an entry

Before CUBE implements anything, the entry here must carry:

. a captured cold-path trace and representative timing;
. the consumer-facing operation and its latency budget;
. the authoritative CUBE resources and permission rules;
. the proposed C-J interface, including pagination and freshness;
. why an existing collection or query expansion is insufficient; and
. a compatibility plan for clients not yet using the projection.
