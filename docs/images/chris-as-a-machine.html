ChRIS: the architecture

docs/linux-metaphor.adoc · docs/bastion.adoc · docs/stratus.adoc · chrisproject.org/docs/guide

ChRIS read as a machine. Rows are layers, each running inside the one beneath; surfaces are not layers, they attach from above over a wire. Two ways in: the mise stack on a bastion, which presents CUBE as a filesystem with processes, and the original web UI, which speaks CUBE's REST API from a browser tab. Below the network line is the server's machine: CUBE and its services, the compute it schedules onto, the cluster, and the substrate the cluster stands on. A PACS is another machine across another network, reached through CUBE's own gateway.

THE BASTION: a container, a VM or a real machine running the mise stack. Its entrypoint starts porter; everything in this box is a process on it, and its own kernel is below the picture. In HARBOR it is the spoke bastion beside a cohort, or the cloud controller at the Hub running a stratus session instead of this one.

The serverfile server and batch system together · NFS server + a batch scheduler

CUBE: the ChRIS backend, one server under both columns. It exports a filesystem and runs programs on it, keeps the register of apps, and is itself a set of processes on the cluster below.

API server
the Django application on uvicorn: Collection+JSON over HTTP, and a WebSocket for PACS progress (LONK). Every surface, chrisapi in both columns, speaks to this and nothing else. · the NFS daemon and the job queue's front
workers
Celery over DragonflyDB (RabbitMQ until 2026-03): queues main1 (start a job), main2 (poll, cancel, clean up). · the batch queue
periodic tasks
celery beat on a database schedule, its own worker and queue: status sweeps, cleanups, PACS bookkeeping. · cron
PACS gateway: pfdcm and oxidicom
pfdcm asks the PACS (query, retrieve); the PACS sends the studies to oxidicom, a DICOM receiver that writes them into storage, registers them, and reports progress over nats. Both columns reach the PACS only through CUBE's own endpoints. · an import daemon and its listener
PostgreSQL
the metadata: users, feeds, plugin instances, PACS studies and series, the register of apps (plugins by name, version, parameters, help). · the inode table and the package database
file storage
the files: CFS, the ChRIS File System, home/<user>/, feeds, SERVICES/, PIPELINES/; Swift, S3 or a POSIX filesystem. chris mounts it at /, the UI reads it over REST. · the disks
what CUBE presents
feeds are process trees, plugin instances are processes, a pipeline is a script that starts several; under mise they are /proc/jobs and /bin, under the UI the feed and plugin tabs.
one job, from the top
a plugin's name typed in chell or clicked in the UI → the API makes an instance → a worker hands it to pfcon → pfcon stages the inputs, runs the container on its engine, stages the outputs back → the worker polls it to its end → the outputs are a node of the feed in CFS.
DICOM both ways: pfdcm queries and asks for a retrieve, the PACS pushes the images to oxidicom. The PACS never sees ChRIS's API; nothing is ever written back to it.
The compute resourcewhere a job's process runs · the batch scheduler and its staging area
pfcon
one per compute resource, the whole of it since 2025-09 (pman was merged into it and is gone). A Flask API under gunicorn: pluginjobs, and copyjobs, uploadjobs, deletejobs that run as small containers of their own on the same engine. · the scheduler and the staging area in one daemon
the storage it stages from
in-network: the same Swift, S3 or shared filesystem CUBE writes (fslink resolves .chrislink); out-of-network: inputs arrive as a zip and outputs go back as one. · the NFS mount, or a copy
the engines
Kubernetes (OpenShift is the same driver), Docker Swarm, Docker or Podman on one host. SLURM through Cromwell was removed in 2025-10. CUBE may be attached to several compute resources at once, chosen per plugin instance.
Distribution and kernelwhat runs where; the machine's state · a Linux distribution on its kernel
OpenShift on Kubernetes
the control plane is the kernel: a pod is a process, a node a CPU, a namespace a user and cgroup, a persistent volume a mounted disk, a Service a port that stays put, an Operator a systemd unit. OpenShift is the distribution: projects, Routes, security context constraints, OLM and the image registry, builds, the web console, oc. CUBE and its services are pods here, installed by Helm through the kubeconfig; a plugin instance is a pod on a node. OpenShift itself lands on the nodes from Red Hat's Assisted Installer. In HARBOR, a Trusted Domain is one such cluster with ChRIS on it and a spoke bastion beside it.
Hardwarewhat the machine is made of · CPUs, memory, disks, network
the substrate: a cloud tenancy
Oracle Cloud Infrastructure first; MOC, CHPC later. Nodes, VCN, subnets, load balancers, volumes, the object store. Laid down by the Hub bastion's stratus session through the tenancy's API key: domain plan, domain build.
on-prem
a hospital's own machines: instances, volumes, networks, load balancers; set up by hand, the same cluster above.

What the older wiring diagram drew (ChRIS_ui, CUBE's API server, workers and periodic tasks, the database and object storage, pfdcm and the PACS, pfcon and the compute cluster) is here, inside the server's box and the compute row, brought up to date: pman is folded into pfcon, RabbitMQ is DragonflyDB, oxidicom receives what the PACS sends, S3 stands beside Swift. What it could not draw is above the line: a door, a session, a shell and a filesystem on a bastion, from which the same server is a machine one types at.
