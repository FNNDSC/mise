CUBE and what it stands on

The ChRIS backend as blocks: who talks to whom, over what, and where each block sits. CUBE is one deployment on an OpenShift cluster; every block in its box is a pod from the Helm chart. A compute resource is a separate pfcon, in-network when it shares CUBE's storage on the same cluster, out-of-network when it does not. The PACS is another machine across another network. Callers above the picture are the mise bastion and the web UI (docs/linux-metaphor.adoc); both arrive as chrisapi. Numbers follow one plugin instance from the call to its outputs.

Who calls
the mise bastion
chris backend: cumin over chrisapi. CFS mounted at /, jobs at /proc/jobs, PACS at /net/pacs.
ChRIS_ui in a browser
chrisapi is the whole stack; the PACS tab listens on the LONK WebSocket.
Neither holds a credential CUBE did not issue: a token from auth-token/, nothing else.
The PACS: another machine
PACS server
the hospital's archive; studies by patient, study and series. Speaks DICOM on its own network: answers finds, honours moves, pushes images.
Never written to. It sees two DICOM peers, pfdcm and an AE called ChRIS; it never sees CUBE's API.
THE CUBE DEPLOYMENT: one Helm release on the cluster below. Every block is a pod; the API and the DICOM listener reach the outside through a Route and a Service, everything else is cluster-internal.
Secrets: the database password, the storage keys, one token per pfcon, pfdcm's address. Patient data lives in the file storage and nowhere else in this box.
API server · Django on uvicorn
Collection+JSON over HTTP; the LONK WebSocket for PACS progress. Validates, records, enqueues. Runs nothing itself.
DragonflyDB · the broker
Celery's queue: main1, main2, periodic. RabbitMQ until 2026-03.
workers · Celery
main1 starts a job at its pfcon; main2 polls it, cancels it, cleans up. One token per compute resource.
beat · the clock
a schedule kept in the database; its tasks run on a worker of their own.
nats · the notice board
receive progress from the listener; the API relays it to browsers as LONK.
PostgreSQL · the metadata
users, feeds, plugin instances, pipelines, PACS studies and series, the register of apps.
file storage · CFS, the ChRIS File System
Swift, S3 or a POSIX filesystem: home/<user>/ and its feeds, SERVICES/PACS/, PIPELINES/. Written by the API (uploads), by the listener (studies), and by in-network pfcon (outputs); read by everyone.
oxidicom · the DICOM listener
a C-STORE receiver, AE title ChRIS, port 11111 through a Service: writes what the PACS sends into the file storage, registers each series through the broker, reports progress to nats.
pfdcm · the DICOM client
finds studies (C-FIND) and asks the PACS to send them (C-MOVE) on CUBE's behalf; the API calls it over HTTP for pacs query and pacs retrieve. Holds the list of PACS services.
Compute, in-network
pfcon · the scheduler
a Flask API under gunicorn, one per compute resource; pman is folded into it since 2025-09. Takes a job over HTTP with its token, turns it into work on its engine, answers status and logs.
op containers · the staging
copyjobs: pull the inputs from the shared storage into the job's incoming/, resolving .chrislink; uploadjobs: push outgoing/ back (a no-op on a shared filesystem); deletejobs: clear the job's directory.
the plugin's container · the process
a Kubernetes Job, one pod, the image from the register of apps, incoming/ and outgoing/ mounted from the storeBase PVC.
Shares CUBE's storage, so inputs and outputs are copies within one filesystem or object store, never a transfer.
Engines: Kubernetes (OpenShift is the same driver), Docker Swarm, Docker or Podman on one host. SLURM through Cromwell was removed in 2025-10.
Compute, out-of-network
pfcon, the same program
on another host or cluster, reached over HTTP with its own token; a different engine, often a plain Docker host.
zip in, zip out
no shared storage: a worker sends the inputs as a zip in the request and downloads the outputs as a zip when the job ends. Slower; needs nothing of CUBE's cluster.
the plugin's container
the same image, run by whatever engine is there.
A site can attach several compute resources at once; the plugin instance names the one it runs on.
The cluster: Red Hat OpenShift on Kubernetes
Helm, the kubeconfig
installs the CUBE release: Deployments for every block above, their Services, the Secrets. · the package manager
Routes and Services
the API's HTTPS route, the DICOM port for the listener. · the firewall and NAT
storage classes
PVCs for the database and the storeBase; the object store beside the cluster. · the disks
the Kubernetes API
in-network pfcon asks it for a Job per plugin instance and per op; the scheduler puts each pod on a node. · the kernel
The substrate
a cloud tenancy: Oracle Cloud Infrastructure first. Nodes, VCN, load balancers, volumes, the object store; laid down by the Hub bastion's stratus session (domain build).
on-prem: a hospital's own machines, set up by hand; the same cluster above.
Elsewhere
another host or cluster
its own engine and disks; nothing of CUBE's cluster reaches it, only the HTTP calls from the workers.
A GPU box in a lab, a partner's cluster, a cloud elsewhere.

One plugin instance: 1 a caller posts it to the API, which records it; 2 the API enqueues it and a worker picks it up; 3 the worker hands it to the compute resource's pfcon with that resource's token; 4 pfcon stages the inputs with a copy op, out of the shared storage in-network or out of the request's zip; 5 it runs the plugin's container, a Kubernetes Job on the cluster when the engine is Kubernetes, 6 which the cluster's scheduler places on a node; 7 the outputs land back in CFS, a copy op in-network or a zip the worker fetches, and the worker, polling on main2, marks the instance finished. A PACS pull is the other loop: the API asks pfdcm, pfdcm asks the PACS, the PACS sends to the listener, the listener writes CFS and registers the series, and the browser watches it arrive over LONK.
