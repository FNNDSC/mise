== Abstract

HARBOR is a fleet of Trusted Domains (TDs), each an OpenShift cluster on its own tenancy holding data that may not move. Its basic need is one primitive: a developer, human or agent, works in one place, the Hub, and runs the same code in many spokes against each spoke's cohort, with only results coming back. Everything else in HARBOR hangs off that primitive: `gather`, policy on what code may see and emit, provenance, the two bastions (<<bastion.adoc#,bastion.adoc>>). This document records what Red Hat's products offer against that primitive, verified against public material on 2026-10-21, and the two mechanisms HARBOR uses to supply it. It is a survey with a date; the products move, the need does not.

The finding in one sentence: Red Hat ships the fleet plane, the per-cluster workspace and the per-cluster compute, and a community pattern that uses the fleet plane for one kind of job; it ships no "code here, run there" loop, and nothing with data policy or an output airlock.

[[need]]
== The need, stated precisely

* *N clusters, one developer.* The spokes are separate OpenShift clusters, each on its own cloud tenancy, each holding a cohort that stays where it is. The developer sits at the Hub.
* *The same code, everywhere, now.* An edit at the Hub runs in every selected spoke against that spoke's cohort. The turnaround is a developer's loop: seconds to minutes, not a release.
* *Only results come back.* Each spoke returns what its policy allows from `/outgoing`: whole, reviewed, or de-identified. Raw data never crosses a TD boundary.
* *Under policy and with provenance.* What the code may read (`/incoming` open or listed) and what may leave are properties of the spoke, set before the code arrives; every run is a node in that TD's ChRIS feed.

Without the primitive each spoke is an island, and multi-site analysis means pooling data, which a Trusted Domain forbids.

[[gap]]
== The gap

The parts exist: a fleet plane (OCM), a per-cluster workspace (Dev Spaces), per-cluster compute (OpenShift AI), a per-cluster build (Pipelines), a fleet-wide sync (GitOps). The composition does not. Specifically absent:

* *A developer's loop across clusters.* No product takes an edit at one cluster and runs it on N others with results returned to the editor. The fleet plane moves state; the workspace is pinned to its cluster; the FL pattern moves one container and returns one artifact.
* *Data policy as a property of the run.* Nothing in the stack knows `/incoming` and `/outgoing`, open or listed, or an airlock on output. Policy engines (Gatekeeper, Kyverno) constrain pods, not what code may see.
* *Provenance tied to cohorts.* No product records "this code, this cohort, this output" as a first-class object. ChRIS feeds do.

This is the thing HARBOR adds on top of OpenShift, and the sentence for a Red Hat audience: *you ship the fleet and the workspace; HARBOR is the loop between them, under policy, with provenance.*

[[mechanisms]]
== Two mechanisms HARBOR uses

Both move code to data; they differ in what moves and how fast.

[[ship-app]]
=== Ship a HARBOR app

The developer at the Hub writes the code, packs it as a HARBOR app (a ChRIS plugin, a container), and ships the container to a collection of spokes with the same cohort mapping as a `gather`. Each spoke's ChRIS runs it as a plugin instance on its cohort; `/outgoing` returns per policy; each run is a feed node. This is the plugin path, and it is the right path for a finished method, a repeated analysis, or a federated-learning round. It is the shape the Red Hat FL pattern has for one workload; HARBOR has it for any plugin.

It is counter-indicated for development. The smallest change rebuilds a container and redistributes it across the network; a `print()` costs the build, the push, the pull and the scheduling, a quarter of an hour where a developer needs a second.

[[ship-code]]
=== Ship the code

The developer at the Hub edits in a dev bastion there; the code, and only the code, is transmitted to the spoke TD's bastion and run there, in a project directory that already has the toolchain and the cohort at `/incoming` under that spoke's policy. Results return from `/outgoing`, again per policy. The image never moves; the runtime is already in the spoke bastion; what crosses the wire is source, and the turnaround is the turnaround of a shell.

This is the mechanism the spoke bastion exists for (<<bastion.adoc#spoke,bastion.adoc>>). In the common case the spoke bastion has no human inside: it is a runner with the sealed policy on, driven from the Hub. The open interactive mode is the exception, for code that cannot be written blind.

What the second mechanism asks of mise, and nothing else supplies:

* *A door per spoke bastion.* The Hub developer holds a dev-space credential for each spoke they may run in (a porter door token), never a cloud key and never a cluster role. The key-ring rule of <<bastion.adoc#posture,bastion.adoc>> holds: each key ring stays inside the boundary it belongs to.
* *Code over the wire.* The Hub session attaches to each spoke's calypso and lands the code in the project directory through the `tasks` tier, then runs it. One edit, N attaches, N runs: the fan-out is the session's, not a fleet controller's.
* *The gate on code, not on images.* In sealed mode the spoke's policy approves the code that may touch `/incoming`; the container was approved when the bastion was made.
* *Results as feed nodes.* Each spoke's `/outgoing` lands in that TD's ChRIS; the Hub reads back what policy allows.

When the code is done, the first mechanism takes over: `plugin build` turns the project into a HARBOR app and the fleet runs it without a developer in the loop.
