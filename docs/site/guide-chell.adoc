= The chell vocabulary: build with the shell's metaphors
:toc: left
:toclevels: 2
:source-highlighter: highlight.js
:example-root: ../../packages/chell/exemplars/ts

== What this is

chell projects ChRIS onto a POSIX shell: files and feeds are paths, plugins are executables, jobs live under `/proc`, PACS queries under `/net/pacs`, and the verbs are the ones every operator already knows. That projection is itself a development surface. A program can speak it two ways: as `.chell` scripts run by the shell (`chell -e -f script.chell`, the analogue of a bash script), and as command lines handed to the engine from TypeScript, where each line returns typed envelopes instead of printing to a terminal.

== Why this is

Sometimes the shell's vocabulary is the right abstraction even when no human is typing: automation that mirrors what an operator would do stays reviewable by that operator, and one line like `pacs pull AccessionNumber:12345678` carries orchestration that would take a page of client calls. The intent API (see the link:guide-intent.html[intent guide]) is the right tool when your program thinks in typed operations; this vocabulary is the right tool when it thinks in operator actions.

== How this relates to the other APIs

Every chell command is a brasa builtin, and the builtins call the same salsa and cumin functions the intent guide documents; nothing here is a second implementation. Driving lines through the engine is the session API (see the link:guide-session.html[session guide]) with the vocabulary as payload, and everything shown here works identically through a remote `RemoteEngine` attached to a daemon.

== The command surface

The vocabulary groups by domain; `help` inside chell is the authoritative, always-current list, and `help <command>` documents each one.

[cols="1,3"]
|===
| Domain | Commands

| Filesystem | `ls`, `cd`, `pwd`, `cat`, `touch`, `mkdir`, `cp`, `mv`, `rm`, `tree`, `du`, `upload`, `download`, `edit`, `pull`
| PACS | `pacs query`, `pacs pull`, `pacs status`, `cubepath`
| Resources | `feed`, `plugin`, `plugininstance`, `pipeline`, `workflow`, `pluginmeta`, `tag`, `group`, `user`, `compute`, `files`
| Jobs | the `/proc` tree (`ls /proc/jobs`, `cat .../status`, `.../log`, `.../params`), `proc refresh`
| Session | `connect`, `logout`, `whoami`, `context`, `version`, `date`, `cal`, `fortune`
| Shell features | pipes (`cat f.txt \| wc -l`), redirection (`>`, `>>`), semicolon batches, `!` host-shell escape, wildcards
|===

== The typed envelope, in detail

Every command in mise, however invoked, concludes in exactly one *command envelope*: the single currency in which results travel from execution to whatever hosts it, a terminal, a daemon, a pipe, or your program. Understanding its four fields is understanding the whole result model.

[cols="1,1,4"]
|===
| Field | Type | Meaning

| `status` | `'ok' \| 'error'` | The command's terminal verdict. This is the error channel: a failed command is an error-status envelope, never a thrown exception, so control flow is a field check rather than a try/catch.
| `rendered` | `string` | The printable output, exactly what a terminal would show (ANSI permitted; the typed API's `cat` disables highlighting so this channel is clean data). Piping, redirection and capture all consume this field.
| `renderedErr` | `string?` | Printable error-stream text, when the command produced any. The place to look, and to show your users, when `status` is `'error'`.
| `model` | `{ kind, data }?` | The same result as data: a discriminated slot whose `kind` names the payload shape and whose `data` carries it. This is what a graphical panel, a bot, or your program reads instead of parsing `rendered`.
|===

=== From untyped slot to `TypedEnvelope<K>`

On the wire and in the shell the model slot is deliberately loose: `kind` is a string and `data` is unknown, so the envelope's shape never changes as commands evolve. The typed API adds the compile-time layer: a *kind map* (`FsModelMap`) declares, for every kind a command emits, the exact payload type its implementation builds, and `TypedEnvelope<K>` is nothing more than a `CommandEnvelope` whose model slot is narrowed to one entry of that map. Structurally the two are identical; the narrowing exists only in the type system, which is why the wire, the REPL and the typed API can share one envelope without conversion.

Each facade method declares its kind in its return type, so the payload arrives typed with no cast:

[source,typescript]
----
const where: TypedEnvelope<'fs.cwd'> = await sh.pwd();
if (where.status === 'ok' && where.model) {
  where.model.kind;        // 'fs.cwd' — the literal, not string
  where.model.data.path;   // string — the compiler knows the shape
}
----

The one place trust enters is a single audited helper (`envelope_typed`) inside the facade: each command core is the sole producer of its kind, so the envelope it returns carries that kind's payload by construction. Nothing downstream ever asserts.

=== The kinds and their payloads

The filesystem vocabulary currently maps these kinds; the map grows as commands join the typed surface, and the generated link:api/modules/_fnndsc_brasa.html[brasa reference] documents each payload interface in full.

[cols="1,2,4"]
|===
| Kind | Payload | Carried by

| `fs.cwd` | `{ path, shown? }` | `pwd`, `cd`: the working directory, and its title-substituted display form when requested.
| `fs.listing` | `LsListing[]` | `ls`: one entry per listed target, each holding the resolved `path` and its `ListingItem[]` (name, type, size, owner, date).
| `fs.mkdir` | `MkdirOutcome[]` | `mkdir`: per-directory `{ path, created }`.
| `fs.touch` | `TouchOutcome[]` | `touch`: per-file `{ path, created }`.
| `fs.cat` | `CatOutcome[]` | `cat`: per-file `{ path, ok, binary, bytes? }`; the content itself is the `rendered` channel.
| `fs.rm` | `RmOutcome[]` | `rm`: per-target `{ path, removed, skipped }`.
| `fs.cp` | `CpModelData` | `cp`: the destination plus per-source outcomes and copied/failed counts.
| `fs.mv` | `MvModelData` | `mv`: the destination plus per-source outcomes and moved/failed counts.
|===

=== Consumption patterns

Three idioms cover practical use. Gate on status and presence, then read data:

[source,typescript]
----
const listing = await sh.ls('data');
if (listing.status !== 'ok' || !listing.model) {
  console.error(listing.renderedErr ?? 'ls failed');
  return;
}
const names: string[] = listing.model.data[0].items.map((item) => item.name);
----

Treat per-target commands as batch reports rather than booleans, because one failed target yields an error-status envelope whose model still reports every outcome:

[source,typescript]
----
const removed = await sh.rm(['a.txt', 'b.txt']);
const failures = (removed.model?.data ?? []).filter((outcome) => !outcome.removed);
----

And keep the channels in their lanes: `model.data` is for logic, `rendered` is for display (or for content, in `cat`'s case), and `renderedErr` is for humans when things fail. A program that parses `rendered` where a model exists is reintroducing the screen-scraping this envelope exists to end.
