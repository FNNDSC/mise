[abstract]
== Abstract

A *Trusted Domain* (TD) is three layers an institution controls: a cloud tenancy, an OpenShift cluster built on it, and a ChRIS deployed on the cluster; the first are on Oracle Cloud Infrastructure (an *OCI TD*). Building one today is the job of `harbor-oci`, a Python command-line harness that turns an empty OCI tenancy into a running ChRIS by driving Red Hat's Assisted Installer, Oracle's `oci-openshift` Terraform stack and the `fnndsc/chris` Helm chart.

This document designs *stratus*: the second backend that issue #977 made room for. A stratus session is *outside* any ChRIS. It reads and changes the substrate — a tenancy's compartments, limits, networks, DNS, buckets, instances and clusters — and builds Trusted Domains on it, with the shell, the console, ARGUS's frame and the session host that ChRIS sessions already have. The cloud is a *driver* inside stratus, not a backend of its own: OCI is the first driver, and a second cloud adds a driver, never a backend. `harbor-oci`'s README names this direction: "building a cluster becomes one more mise backend, with a web interface and a console for `oc` and friends".

It builds on `docs/backend-neutral.adoc` (#977), whose engine, descriptor, registry, tasks and ARGUS compositions it uses, and whose two rules it keeps: one backend per session, and nothing changes for a ChRIS user. *Status: proposal revised with the operator 2026-10-20 (first draft 2026-10-10). Nothing is built before the operator approves the revision.*

[[names]]
== The name

The word for a layer cloud, and the sound of *stratum*: the layer a thing rests on. One word names three things, as `chris` does for the ChRIS backend: the package `@fnndsc/stratus`, the backend id `stratus` the attach handshake carries, and the ARGUS composition `compositions/stratus/`. The first draft proposed `hearth` and a backend id `oci`; both withdrawn. `hearth` sounds like the opposite of a cloud, and `oci` named the backend after one driver.

[[two-sessions]]
== Two sessions, two places

A Trusted Domain has an outside and an inside, and mise gives each its own session:

[cols="1,2,2",options="header"]
|===
| | The substrate session | The domain session
| Backend | `stratus` (this document) | `chris` (today's)
| Connected to | a cloud tenancy, through the driver's credential (OCI: an API-key profile) | the CUBE the build produced
| What it acts on | compartments, limits, networks, DNS, buckets, instances, the OpenShift cluster | feeds, plugins, files, PACS
| Who uses it | whoever builds and runs the domain | researchers and clinicians inside it
| Credentials it holds | cloud API key, Red Hat service account, cluster admin | a CUBE token
| Brand | the TD mark in the driver's ring (OCI: Oracle red) | the TD mark, and a domain segment in the prompt
|===

They are separate calypso daemons, as #977's <<backend-neutral.adoc#one-backend,one backend per session>> requires: one process never holds cloud credentials and a CUBE token together. ARGUS can show both as two attached sessions; the substrate session hands off to the domain session when a build finishes (<<handoff>>).

[[bastion]]
=== The bastion, and chell as the surface

The substrate daemon runs on one host, the *bastion*: the machine that holds the cloud credential, the Red Hat service account, the SSH key and, once a domain is built, its kubeconfig. Today it is the operator's workstation; later a small instance inside the tenancy, using an instance principal (<<identity>>). Nothing else ever holds those files.

chell on the bastion is the surface that drives a Trusted Domain: `suggest`, `domain new`, `domain plan`, `domain build`. ARGUS drives it the same way, because since #1125 the ARGUS console is a chell running on the daemon's host under a pty: typing in the browser is typing at the bastion. There is no web-only path to start a step; a control on a pane or on the controller (<<controller>>) runs a console line, as #1082's law says a view is a script. What ARGUS adds is watching and shaping: tiles, the domain pane, the log view, the controller, the brand.

[[three-layers]]
=== Three layers, three tools, one spec

Each layer has a tool today: the cloud is Terraform and the SDK; the cluster is the Assisted Installer and `oc`; the application is Helm and the seed. The first draft described the cluster in a spec and the application only as three step names and a chart version, so "deploys ChRIS to it" had nothing to deploy from. One spec, two halves: `spec.yaml` holds the cluster (CPU family, control-plane and worker pools in vCPU and GiB, boot disks) and the ChRIS on it (chart version, `dataGib`, `databaseGib`, `queueGib` as `harbor-oci` already has them, the compute backend, the PACS to connect, the seed users). `domain plan` prices and checks both; `domain build --through verify` builds the machine, `domain build` to the end installs the application.

[[findings]]
== What exists: harbor-oci

Surveyed in `~/src/harbor-oci` on 2026-10-10; unchanged since (last commit 2026-10-08). A Typer CLI (`harboroci`, `cli.py`) wrapped by a `justfile`; `just install` runs the build in order: `preflight cluster iso infra-plan infra-apply dns manifests hosts run postinstall verify` (`justfile:22`).

[cols="1,3",options="header"]
|===
| Step | What it does
| preflight | Tools present (`terraform`, `oc`, `helm`, `dig`); no secrets inside the clone; API key, compartment, attribution tag namespace; the spec fits per-AD limits and three flexible load balancers are free; DNS delegation; the Red Hat account; the SSH key (`preflight.py`).
| cluster | Creates the Assisted Installer cluster and infra-env (`steps.py`, `assisted.py`, `redhat.py`).
| iso | Downloads the discovery ISO into an Object Storage bucket and makes a pre-authenticated request for it (`ocistorage.py`).
| infra-plan | Fetches the `oci-openshift` stack (SHA256-pinned), writes tfvars from `spec.yaml`, `terraform init` and `plan` (`stack.py`).
| infra-apply | Refuses a plan that updates or destroys existing resources, then `terraform apply`. *Billing starts here.*
| dns | Upserts the `api`, `api-int` and `*.apps` records in OCI DNS (`ocidns.py`).
| manifests | Pushes the stack's custom manifests (OCI cloud controller and CSI drivers) to the Assisted Installer.
| hosts | Waits for the hosts to register (up to 45 minutes), assigns roles.
| run | Installs OpenShift (up to 120 minutes, polled each minute); saves the kubeconfig and the kubeadmin password.
| postinstall, teardown | Placeholders (exit 2, "not yet proven").
| verify | Ten live checks through `oc` and `dig` (`verify.py`).
| chris-deploy, chris-seed, smoke, chris-nuke | Helm install of ChRIS, a seed job, the smoke suite, removal (`chris.py`).
|===

Read-only verbs beside the build: `status`, `deployed`, `burn` (spend so far), `capacity`, `shapes`, `spec`, `suggest` (sizing).

* *OCI access* is the Python SDK: Identity (tenancy, compartments, tag namespaces, availability domains), Limits, DNS, Object Storage, Compute, Block Storage, Load Balancer and Resource Search ("all resources where compartmentId = …"). Terraform builds the VCN, subnets, security groups, load balancers, image, instances, dynamic groups and policies. `oc`, `helm` and `dig` run as subprocesses; the Red Hat APIs over REST; prices from Oracle's public price list.
* *Authentication* is an API-key profile in `~/.oci/config`; the region is forced from settings. Settings come from the environment over `config.local.env` over `config.env` (`OCI_REGION`, `OCI_PROFILE`, `OCI_COMPARTMENT_OCID`, `BASE_DOMAIN`, `CLUSTER_NAME`, the Red Hat credentials, pinned versions).
* *State* is `state/harbor.json` (cluster and infra-env ids, the ISO object and its link; mode 600, written atomically), Terraform's state in the staged stack, and credentials in `state/auth/`.
* *One region, one domain:* `us-ashburn-1`, base domain `oci.chrisproject.org`, cluster `harbor`. Nodes spread one per availability domain.
* *The cloud seam already exists there:* `TenancyProvider` (`capacity.py`) and `PriceProvider` (`pricing.py`) with OCI subclasses, and a spec in vCPU and GiB. Its own analysis: "Roughly 70 percent of the code is bound to OCI" and "The install path makes no attempt at a cloud abstraction. The tenancy tools do" (`docs/overview.adoc`).
* *Known open problems:* OCI's automatic `Oracle-Tags` make a re-plan want to alter 24 resources, so `infra-apply` refuses alterations and clean re-plans are undecided; `teardown` has never been run, and the compact cluster has billed about $0.71 an hour since 2026-10-07 (`docs/status.adoc`).

[[precedent]]
== Argue from the tree that exists

The first draft drew its tree from `harbor-oci`'s shape and invented three roots (`/tenancy`, `/regions`, `/domains`). The operator saw at once that a ChRIS session already has a place for a remote world: `/net` (`/net/pacs/queries/<query>/<study>/<series>`), with processes under `/proc` and executables under `/bin` (`chris/navigation.ts`, `CHRIS_STRUCTURAL_PATHS`). *Every path, item kind and verb in this document is checked against what a ChRIS session mounts before it is proposed*, and a proposal names its precedent. A new backend joins a tree; it does not redraw one.

[[decisions]]
== Decisions

Each was put to the operator on 2026-10-20 and agreed unless marked otherwise.

[[one-backend-many-clouds]]
=== D1. One backend, clouds as drivers

Two shapes were weighed. *A backend per cloud* (`oci`, `aws`, `gcp`, …): four trees, four prompts, four compositions saying DOMAINS, CAPACITY and STEPS, and a fifth package for what they share. *One substrate backend with the cloud as a driver inside it*: the tree, the `domain` verbs, the task source, the prompt segments and the ARGUS composition written once; a cloud is a set of providers behind one interface, which `harbor-oci` already drew. The second is chosen.

What differs between clouds, as the session sees it, is small and named: how containers nest and what they are called, where a region sits, the credential and identity, the limits, shapes and prices, the infrastructure plan and apply (a per-cloud Terraform stack). The Assisted Installer and the Helm chart are the same on every cloud. <<tree>> says how four clouds map onto one tree.

The caution from #977 applies with more force: an abstraction drawn from one cloud takes its shape. Three guards:

* *A driver interface and a ratchet.* `CloudDriver` lives in `src/cloud/driver.ts`; OCI implements it in `src/cloud/oci/`. The count of files outside `cloud/oci/` that import an `oci-*` package starts at zero and may never rise (`lint:stratus-deps`, built like `lint:core-deps`).
* *A fake driver.* An in-memory cloud (`src/cloud/fake/`) runs the same driver contract suite the OCI driver runs, so the interface stays real with one cloud, as fond's null provider does for the filesystem.
* *No second driver is written before a second cloud is real.* The fake is a test, not a product.

[[package]]
=== D2. The package `@fnndsc/stratus`, and how a daemon hosts it

`packages/stratus/` in this repository while the descriptor is still settling, as #977's cautions advise. It depends on brasa's core (`@fnndsc/brasa/core`), fond, menu and calypso, and on Oracle's TypeScript SDK as per-service packages (`oci-identity`, `oci-limits`, `oci-resourcesearch`, `oci-objectstorage`, `oci-dns`, `oci-core`, …) rather than the whole `oci-sdk`. It never loads cumin, salsa or chili; CI gets a stratus boot beside brasa's core boot that fails if one is loaded.

*How calypso hosts it.* Four ways were weighed: calypso depending on stratus (every ChRIS install would pull the OCI SDK: wrong direction); calypso importing `@fnndsc/<id>` by flag (an allowlist and a version-skew problem); a config file mapping ids to modules (the same, with more machinery); and *stratus shipping its own launcher*. The last is chosen for now: the `stratus` command imports calypso's `daemon_launch`, creates the engine with `engine_create(stratusBackend_make(...))`, and hosts it. Nothing in calypso changes, the dependency arrow points from stratus to calypso, and #977's picture already drew it ("chell, porter and the calypso launcher each compose the engine with exactly one backend"). A substrate daemon is started by hand on the host that holds the cloud credential. porter starting one is deferred with porter's second tier, and brings its own question: a substrate session has no CUBE password, so its door is a different thing.

[[port]]
=== D3. Read in TypeScript first; wrap the build, port it step by step

* *Everything that reads* — the tree (<<tree>>), limits, capacity, shapes, prices, spend — is written in stratus against the SDK from the start. It is where a session spends most of its time, and it is safe.
* *The build steps* first run as `harboroci <step>` under the supervised runner (<<tasks>>): proven code keeps doing the work while the session gives it a console, a log, progress and a place in ARGUS. Each step is ported into the driver when it is next changed, and the harness retires when the last one goes.
* *Terraform, `oc` and `helm` stay external tools*, always run by the supervised runner, never reimplemented.

[[tree]]
=== D4. The tree: a tenancy is a mount under `/net`

Precedent: `/net/pacs/queries/…` is a remote server and then what it holds. A cloud tenancy is a remote filesystem the session mounts, as NFS mounts under `/net`.

[literal]
....
/
├── home/<user>/                       the core's home: the operator's own files (drafted specs, suggest --save)
├── net/
│   └── oci/                           the driver's mount; a second cloud would be /net/aws
│       └── fnndsc/                    a tenancy, by display name: the root compartment
│           ├── harbor-oci/            a compartment; nested compartments nest
│           │   ├── instances/node-0/  name id state region created tags info.json  shape zone ips
│           │   ├── networks/vcn/      subnets/<subnet>/  securitygroups/<group>/  info.json
│           │   ├── loadbalancers/api/ … ip shape
│           │   ├── volumes/node-0/    … size attached
│           │   ├── buckets/iso/       its objects are files; an object has a field `link` (its PAR)
│           │   └── dns/<zone>/        its records are files
│           ├── regions/us-ashburn-1/
│           │   ├── zones/<zone>/              OCI: an availability domain
│           │   ├── limits/<service>/<limit>   value used available
│           │   ├── shapes/<shape>
│           │   └── prices/<shape>
│           └── domains/               the Trusted Domains built in this tenancy: the session's home
│               └── harbor/
│                   ├── spec.yaml  state.json
│                   ├── steps/01-preflight/   state log started ended
│                   ├── cluster/              api console version   the cluster, through the Kubernetes driver
│                   │   ├── nodes/<node>/     state roles zone cpu memory
│                   │   ├── operators/<op>/   state version
│                   │   └── projects/chris/   deployments/<d>/  pods/<pod>/ (state node started log)
│                   │                         services/  routes/  pvcs/  configmaps/  events
│                   └── resources/            links into the compartment: what this domain owns
├── proc/steps/                        the steps running now (a task source; the core mounts it)
└── bin/  etc/  usr/                   the core's
....

* *One shape for every cloud:* `/net/<cloud>/<root>/<container>/…/<kind>/<name>`. Four clouds map onto it; what differs is how containers nest, where a region sits, and what a zone is called.
+
[cols="1,1,2,2,1",options="header"]
|===
| Cloud | Root | Containers (nest) | Region | Zone
| OCI | tenancy | compartments, any depth | orthogonal to compartments; an API client per region | availability domain
| AWS | account (alias, else id; or the organization) | none below the account: resource groups are tag views | the primary partition; an API per region | availability zone
| GCP | organization | folders, then a project | an attribute of a resource | zone
| Azure | tenant | management groups, a subscription, a resource group | an attribute of a resource | availability zone
|===
+
The path carries names only; the container noun (compartment, account, project, folder, subscription, resource group) is the row's type in `ls -l`. The driver answers `containers_list(parent)`, so OCI nests arbitrarily, Azure three fixed levels, AWS none, under one path grammar.
* *Region is the session's, not the path's.* The session has one region (<<prompt>>, the `region` verb), and the tree lists that region's resources; `regions/` under the root holds every region's facts; global kinds (DNS zones; buckets on AWS and GCP) list regardless. Every resource has a `region` field. A region segment in the path would be real on AWS and faked on OCI and GCP, and an `ls` on AWS that fanned out over twenty regions would never be quick; `harbor-oci` already forces one region, so OCI loses nothing.
* *Kind folders are generic nouns; native detail is in `info.json`.* Every cloud has `instances networks subnets securitygroups loadbalancers volumes buckets dns`, so the `domain` verbs and the tiles touch only those. A driver may add native kinds nobody else has (OCI: dynamic groups) as extra folders. OCI's NSGs are `securitygroups`, its availability domains are `zones`.
* *No new root.* Only `/net/<cloud>` is claimed, and a session has one cloud. `/net/oci` lists one tenancy today (one API-key profile is one tenancy); the level stays because the path says which tenancy you are in, and `~/.oci/config` can hold several profiles. Whether one session should ever mount two is a posture question for later; the shape allows it.
* *Everything under the tenancy.* Limits are per tenancy per region; a domain is built in one tenancy. So `regions/` and `domains/` sit inside `/net/oci/<tenancy>/`, one rule, rather than beside it. Shapes and prices repeat per tenancy, harmless with one.
* *Compartments beside kind folders.* `/net/oci/fnndsc/` holds child compartments and the kind folders at one level, as OCI's own compartment view does; `ls -l`'s type column (`compartment` against `instance`) tells them apart. The kind folders are reserved names: a compartment called `instances` shows as `instances~<last six of its OCID>`.
* *Kinds in the tree, first:* `instances networks loadbalancers volumes buckets dns`; subnets and security groups nest under their network. Images, policies, dynamic groups and tag namespaces stay out until a verb wants them; they appear in a parent's `info.json` where OCI returns them.
* *Field files.* Every kind: `name id state region created tags info.json`. Per kind on top: an instance `shape zone ips`, a volume `size attached`, a load balancer `ip shape`. The rule `/proc/jobs` follows: a field is a file when a shell line wants it (`cat state`, `grep running`); everything else is in `info.json` only.
* *Names, not OCIDs, in paths.* The OCID is the field `id`. OCI allows two resources in one compartment to share a display name, so a duplicate shows as `name~<last six of its OCID>` and the plain name refuses ("ambiguous: name~1a2b3c, name~9f8e7d"), never picks one. The rule holds wherever a path is resolved: `cd`, completion, globbing and `@N` expansion.
* *Structural paths* (`cd` without a lookup, as `CHRIS_STRUCTURAL_PATHS`): `/net`, `/net/oci`, `/net/oci/<tenancy>`, each kind folder, `regions`, `domains`.
* *The cluster is under its domain*, not a root of its own: built in that tenancy by that domain's steps, reached with that domain's kubeconfig. The Kubernetes driver that serves it is the same on every cloud, so it is a second driver kind (`cluster/`) beside `cloud/`, never inside a cloud driver. The linux-metaphor note already drew it ("projects as folders; deployments, pods and routes as entries in them"). Read-only in the tree; `oc` and `helm` under the `tasks` tier are the write path. This closes the first draft's open question of `oc` against a Kubernetes provider: both, each for what it is good at.
* *Home is the tenancy's `domains/`*, because building and running domains is the session's purpose; the prompt shows it as `~`. `/home/<user>` is the core's and holds the operator's own files.
* *Listings walk.* A compartment can hold thousands of objects; the tree follows the house rule that an unbounded ask walks and a bounded one says what it shows. Listings cache with a short life, refresh in the background, say when they serve a cached answer, and `--fresh` forces, as ChRIS listings do.
* *Disconnected.* No `~/.oci/config`, a missing profile or a refused key: the daemon still starts, with identity `disconnected@oci` (ChRIS: `disconnected@no-cube`). `/net/oci` lists empty with one note, `ls` elsewhere works, the `domain` verbs refuse "not connected". The credential is a file on the host, not a password, so there is no in-session login: fix the profile and restart.

[[rows]]
=== D5. What a row is: numbered as a folder, drawn as a resource, labelled by the cloud

Three fields of a listing row do three jobs, and only one gains anything new.

* *Numbering kind* (`answerKinds`, `@KIND N`). An index expands to a path; the kind says what a verb may be handed and whether a group row hands on its children (ChRIS: `pull` takes SER, STD and PAT and refuses a DIR; a study handed whole gives its series). Every stratus row is a path and no stratus verb needs to refuse by kind or expand a group, so stratus registers *no kinds*: rows are DIR and FIL, `cd @3`, `cat @2/state`, `domain build @1` work by path. A kind earns its place when a listing's rows are not paths or a verb must refuse by kind; the first such listing is `domain plan`'s output, where one change among the `Oracle-Tags` drift must be nameable (`--allow @CHG4`). That kind arrives with that verb (<<order>>, step 4), not before.
* *Item type* (`ListingItem.type`, an open string; the backend's `ListingLook`). How `ls -l` draws the row: mark, colour, container, size column. Stratus adds the container nouns (`compartment`, and on other clouds `account project folder subscription resourcegroup`) and `instance network subnet securitygroup loadbalancer volume bucket object dnszone record domain step`, and for the cluster `node operator project deployment pod service route pvc configmap`, coloured by lifecycle state as jobs are by status: running green, stopped dim, provisioning amber, failed red.
* *Tags* (`ListingItem.tags`). ChRIS fills it with a user's tags on files (`/proc/tags`). Stratus fills it with the cloud's tags, freeform and defined, so the attribution tag (`openshift-tags.openshift-resource=<domain>`) shows in `ls -l` and `grep` over a listing (#1101) finds every row a teardown would take.

[[writes]]
=== D6. Read-only by default; a domain changes through plans

The substrate bills by the hour and some of it cannot be recreated. The session therefore changes the cloud only in ways that say what they will do first:

* *The core file verbs mutate only data:* objects under `buckets/<bucket>/` (`cp`, `rm`, `mv`, `>`; large objects stream both ways through the descriptor's `files.stream`) and records under `dns/<zone>/` when the zone is a domain's own. On any other resource they refuse by name ("rm: /net/oci/fnndsc/harbor-oci/instances/node-0: Operation not permitted: a domain's resources change through `domain`").
* *A record is a file per record name* (`api`, `api-int`, the wildcard), its content the record set as zone-file lines; `>` replaces the set. The wildcard's file name is settled with the step that writes it.
* *A domain changes through `domain` verbs that plan first:* they print what will be created, changed and destroyed, with the estimated hourly cost, and ask before acting. `harbor-oci`'s rule stays: a plan that alters or destroys existing resources is refused unless the operator asks for it by name, and `domain plan` says which alterations are `Oracle-Tags` drift rather than hiding them or crying wolf.
* *Destruction is scoped by attribution.* The build tags what it creates (the attribution tag namespace preflight already checks); teardown removes only resources carrying this domain's tag, and refuses anything else even inside the domain's compartment.
* *Live tests mutate only in a scratch compartment* (`zz-mise-<epoch>`), never in a compartment holding a domain, as the CUBE lesson taught.

[[commands]]
=== D7. Commands

Core commands (`ls`, `cd`, `cat`, `cp`, `find`, `grep`, `wc`, `head`, `sort`, …) work over the tree unchanged, because they use only fond's filesystem. The backend registers, in shell metaphors and with the help categories #1102 made every command carry:

[cols="1,3",options="header"]
|===
| Command | What it does
| `domain new <name> [--spec file]` | Creates `domains/<name>` with a spec (from `suggest`, a file, or the defaults).
| `domain plan [<name>]` | Preflight and the infrastructure plan; prints the changes and the hourly cost; names tag drift.
| `domain build [<name>] [--through <step>]` | Runs the build's steps in order as tasks, from the first not done; stops after `--through`.
| `domain status`, `domain verify` | Where each step stands; the live checks.
| `domain teardown <name>` | Plans removal of everything carrying the domain's tag, shows it, asks.
| `domain attach <name>` | Opens the domain session against the domain's CUBE (<<handoff>>).
| `domain` | In ARGUS, opens the TD controller (<<controller>>); in chell, `domain status` for every domain.
| `limits`, `capacity`, `shapes`, `prices` | What the region allows, has free, offers and charges.
| `spend [<name>]` | What a domain has cost so far and costs per hour (`burn`).
| `suggest` | Sizes a spec from workload figures (`--workers`, `--worker-ram`, …).
| `region [<name>]` | Shows or changes the session's region; the prompt follows.
| `oc`, `helm` | Run against the domain the working directory is in, with its kubeconfig, under the `tasks` tier.
|===

There is no `terraform` command: Terraform runs only inside `domain` steps, where its plan is checked. The `oci` command-line tool is reachable only through the `!` shell tier, like any host program; since #1096 `!` runs in the terminal's pty, so `oci` and `oc` are interactive there.

[[identity]]
=== D8. Identity and credentials stay on the daemon's host

* The driver supplies the identity. For OCI the daemon reads an API-key profile from `~/.oci/config` (`--profile`, default `DEFAULT`); instance principals come later, for a daemon running inside the tenancy.
* The identity is the IAM user's name (looked up from the user OCID) at the tenancy's name: berth `rudolph@fnndsc`. The same `user@tenancy` form on every cloud. The region belongs to the session, not the identity, so changing region keeps the berth.
* The Red Hat service account and the SSH key are daemon settings, as in `harbor-oci`'s `config.local.env`.
* *Secrets are never files the browser can read.* `domains/<td>/cluster/` shows `console api version nodes/`; the kubeconfig and the kubeadmin password live on the host under the domain's state, and `cat` and `/vfs` refuse them with the host path. `oc` and `helm` under the `tasks` tier read the kubeconfig on the host themselves. How an operator gets the console password is <<open,open>>; whatever it is, it is never through the browser.

[[prompt]]
=== D9. The prompt says where in the substrate you are

The wire's prompt context is ChRIS-shaped (`user`, `uri`, `cwd`, `pacsserver`, `physicalMode`, `procWarmup`, and since #1128 `questions`). It gains an optional, backend-neutral list of *segments* — each a key, a label, a value and a tone — that a backend fills and the composition draws in order. ChRIS's fields and prompt do not change; an older daemon sends no segments and an older surface ignores them.

The stratus prompt, the leader segment from the driver:

[literal]
....
◆ OCI │ fnndsc │ us-ashburn-1 │ rudolph │ harbor │ ~/harbor/steps │ 4s
       tenancy   region         user      domain   working directory  last command
....

The domain segment appears when the working directory is inside a domain or one of its resources. A running step adds a segment with its name and progress. Disconnected, the leader reads `OCI ✗`.

[[tasks]]
=== D10. Build steps are tasks; the supervised runner stops being deferred

#977 deferred the supervised runner and its `tasks` tier (#986) "until the second backend actually starts". This is that start:

* Each build step is a task in stratus's task source, under `/proc/steps` and in the domain's `steps/` folder: state, structured progress, log tail, start and end.
* The runner starts the host process (`harboroci <step>` first, the driver's own code later, `terraform`, `oc`, `helm`), keeps its full log on the host, survives a closed browser, and reattaches. It is *not* the terminal's `!` path (#1096): that runs a child of one chell under one pty and dies with it; a step outlives any surface.
* A step's live state travels as the wire's `event` message (kind `stratus.step`, added by #1157 for trek) when a pane wants more than the progress schema carries; the progress schema carries what the prompt and the STEPS tile need. Decided when the first pane is drawn.
* *Cancelling is gentle.* Terraform interrupted mid-apply can leave state locked or half-written: cancel sends one interrupt and waits for Terraform to finish its current operation; it never kills hard. A second cancel says so instead of escalating.
* The `tasks` tier is off by default, separate from `shell` (the tiers today: `shell`, `files`, `pipes`), so a session can run build steps without allowing arbitrary `!` commands. A ChRIS session never enables it.

[[argus]]
=== D11. The ARGUS composition `stratus`

* *Brand:* the TD mark in the driver's ring (OCI: the Oracle-red ring) in the header, its ASCII in the splash, its favicon, the credit line "a Trusted Domain console", through the composition-owned brand seams PR #1054 made (`data-composition`). The red ring is Oracle's mark in all but name; public use needs Oracle's agreement.
* *Tiles:* DOMAINS (each domain, its last step and state, its hourly cost), CAPACITY (headroom per availability domain for the shapes a spec needs), TENANCY (compartments and resource counts by kind), STEPS (running and recent, with progress).
* *Panes:* a domain pane listing its steps as rows with progress, as RUNS lists jobs; the frame's view pane following a step's log; later a topology view in orrery — networks, subnets, load balancers and nodes as a graph.
* *Signals:* the prompt segments (<<prompt>>), and telemetry of resource counts, running steps and the domains' combined hourly cost.
* The tiles and panes are the glance: what a dashboard shows while something else is going on. Working on a domain happens in the controller (<<controller>>).

[[controller]]
=== D13. The TD controller: a screen over the engine, as the trek bridge is

`docs/trek.adoc` built a full-screen ARGUS surface over an engine without changing the engine: the engine shows its state before each prompt, a typed `event` carries it, the bridge takes the screen, and plays by answering the engine's questions with lines built from its controls; nothing moves without an engine line behind it. The TD controller is that pattern over the domain machine:

* *The engine* is stratus's domain machine, already driven by console lines (`suggest`, `domain new`, `domain plan`, `domain build`, the questions it asks before billing).
* *The state shown:* a `stratus.domain.state` event before every prompt and on every change: the spec, each step's state and progress, the cost so far and per hour, the cluster's readiness, and what changed since the last event (the diff the trek header shows).
* *A takeover.* `domain` with no arguments in the ARGUS console opens the controller full screen; LEAVE returns, as trek's bridge does. Same reasons as trek's "why a takeover": a build holds the lane for two hours, and a pane among panes would mislead. In chell the same lines play as text.
* *The screen,* in trek's layout under ARGUS's theme: the header carries the domain's condition (sizing, building, up, billing, failed), its cost and the time in the current step; the gutter holds the views, OVERVIEW, SIZE, BUILD, CLUSTER, CHRIS, TEARDOWN and LEAVE; a view changes the body, a command works in place. SIZE is `suggest` as controls: sliders for workers, worker RAM, ChRIS data, with fit and cost live from `regions/`. BUILD is the steps as a strip, the running one with its log. CLUSTER and CHRIS read `cluster/`. TEARDOWN is the attribution-scoped plan and its question.
* *The controls follow the value.* A slider commits as `domain new --workers 2 …`; BUILD's pill sends `domain build --through run`; the engine's "billing starts at this rate, continue?" is answered by a pill and never skipped. Nothing on the screen starts anything without a console line behind it: #1082's law, and trek's `a-frame-replays-a-printed-line`.
* *The one difference from trek:* a game dies with its surface, a build does not. The controller attaches to a step already running, so the state must be replayable on attach: the task source is the baseline, the event the delta. Trek's event is live only; this one is not.
* *Order:* a mockup page first, grilled, as trek's was; built after step 4 (<<order>>), when the runner and the steps it drives are real. The tiles of <<argus>> are the glance; the controller is where a domain is worked on.

[[handoff]]
=== D12. From building a domain to working in it

When a domain's ChRIS is deployed, the domain records its CUBE address. `domain attach` (and a button on the domain pane) starts the domain session: a separate daemon on the ChRIS backend, logged in through the domain's own sign-in, which ARGUS shows as a second attached session wearing the TD brand with a domain segment in its prompt. The substrate session never holds the CUBE token, and the domain session never holds cloud credentials.

[[order]]
== Order of work

Each step is one change or a short series, released on its own; nothing changes for a ChRIS session at any step.

. *Read the tenancy.* (a) `packages/stratus` with the descriptor, the driver interface, the fake driver and the contract suite, the OCI driver's identity and compartments, the tree for `/net/oci/<tenancy>/` (compartments) and `regions/` (availability domains, limits, shapes, prices), the `stratus` launcher, the stratus boot and `lint:stratus-deps` in CI. (b) the prompt segments on the wire, and ARGUS's `stratus` composition with its brand and prompt only. AEGIS rows with (b).
. *Resources.* Instances, networks, load balancers, volumes, buckets and DNS in the tree, through Resource Search and the service clients; `ls -l` types and states; cloud tags in `tags`.
. *Domains, read.* `domains/` over an existing `harbor-oci` state folder — the live compact cluster as the first domain — with `domain status`, `domain verify` and `spend`; the DOMAINS and CAPACITY tiles.
. *The supervised runner and the `tasks` tier* (#986), shaped by the build's real steps; `domain plan` and `domain build` run `harboroci` steps as tasks; the plan-row answer kind; STEPS tile and domain pane.
. *The cluster in the tree.* The Kubernetes driver over a domain's kubeconfig; `cluster/` fills in; the CLUSTER and CHRIS halves of the spec; `chris-deploy`, `chris-seed` and `smoke` as steps.
. *The TD controller* (<<controller>>): the state event, the takeover, the views; mockup and grill first.
. *Data writes.* Bucket objects and a domain's DNS records through the core file verbs.
. *Teardown,* designed on its own when it is reached: `harbor-oci`'s placeholder becomes an attribution-scoped plan. It must first be run once by hand there, as every harbor-oci step was.
. *The handoff* to the domain session, and the TD brand on it.
. *Porting,* step by step into the OCI driver, until `harbor-oci` retires.

[[tests]]
== Test strategy

* *The driver contract suite,* run by the fake driver and by the OCI driver against recorded answers (the SDK clients behind the interface, replayed from recorded responses with identifiers scrubbed).
* *A stratus boot in CI* that loads no ChRIS package, beside brasa's core boot, and the `lint:stratus-deps` ratchet (no `oci-*` import outside `cloud/oci/`).
* *Live, read-only,* against the tenancy on every change that touches the tree.
* *Live mutation only in a scratch compartment,* torn down by the test; never against a compartment holding a domain, and never against the running cluster.
* *ChRIS unchanged:* the existing unit, smoke and end-to-end suites stay green on every step.

[[security]]
== Security

* *The creator posture* (cloud API key, Red Hat account, cluster admin) lives only in a substrate daemon; the research posture only in a domain daemon (<<two-sessions>>).
* *Host control stays per daemon and off by default:* the `tasks` tier for build steps, `shell` for `!`; the guard refusing a non-loopback bind with any tier on, unless `--expose-host-control` is given, applies unchanged.
* *Secrets never cross `/vfs`* (<<identity>>).
* *Spending asks first:* a step that starts billing shows the hourly cost and asks, and a plan that alters existing resources refuses unless asked for by name (<<writes>>).
* *A browser that reaches the bastion's daemon can spend money,* because its console is a chell on the bastion (<<bastion>>). That is the same power `!` has, gated the same way: the `tasks` tier is chosen at launch, and a non-loopback bind with it on refuses without `--expose-host-control` and a porter door.

[[cautions]]
== Cautions

* *One cloud draws the abstraction.* The driver interface, the fake driver and the ratchet are the answer (<<one-backend-many-clouds>>); a second real driver is the test.
* *`Oracle-Tags` drift.* Until clean re-plans are solved, every re-plan of a built domain shows alterations; `domain plan` must say which are tag drift.
* *Duplicate display names* are common in OCI, and Azure subscriptions share names too; the suffix rule (<<tree>>) has to hold everywhere a path is resolved. AWS accounts are numbers: the alias when set, else the id.
* *Rate limits and size.* Resource Search and the Limits API throttle; listings cache and refresh in the background.
* *One region, one domain* is all `harbor-oci` has proved; the tree and prompt allow more, but the build is not claimed for more until it has been done.
* *The descriptor will move again.* It was drawn from ChRIS and checked by the null backend; stratus is the first real second backend, and the descriptor should change where stratus shows it is wrong, rather than stratus bending around it.
