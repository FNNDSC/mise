= trek: a game as the first package built as if from outside
:toc:

trek is BSD trek(6), the 1976 Berkeley space war game, ported line for line to TypeScript. It plays three ways: as `bsd-trek`, a package anyone installs from npm to play in a terminal; as `trek` in chell, mise's shell; and, to come, as a bridge in ARGUS that takes the whole screen. This document records the decisions behind that, settled with the operator on 2026-10-18, and the order of the work.

trek also matters beyond the game. It is the first part of mise built inside the monorepo as if it came from outside: it imports nothing of mise, and what it needs from mise becomes mise's public contract rather than a reach into its internals. Contracts for outside contributions are drawn from this consumer instead of being designed ahead of any.

== The package

`packages/trek` publishes as `bsd-trek`.

[cols="1,3"]
|===
| Decision | Why

| Name `bsd-trek`, unscoped
| The name a casual player searches for and types (`npx bsd-trek`); it says what the game is. A toy does not belong under the FNNDSC scope, and a neutral org is a decision deferred (below). Plain `trek` on npm is a Rails CMS; no terminal trek game was on npm before this.

| Commands `trek` and `bsd-trek`
| `trek` is the game's name, as in trek(6). `bsd-trek` matches the package, so `npx bsd-trek` and a typed `bsd-trek` behave the same, and a machine where `trek` is something else still has a way in.

| BSD-3-Clause for the whole package
| The original's licence travels with the port; the code written around it (the command, the terminal wiring, the styled scans) is too small to carve out under another. `LICENSE` holds the Regents' notice, the port's copyright line and the original's credits.

| One engine
| The engine lives only in `packages/trek`. brasa's `trek` builtin is a thin consumer (the session's terminal and saved-game slot); the ARGUS bridge will be another. A fix lands once.

| `engines: node >=22`
| What CI tests (22 and 24); Node 20 reached its end of life in April 2026. npm warns at install rather than failing mid-game.

| The CLI behaves as the session's `trek`
| The same flags (`--classic`, `-f`/`-s`, `--seed N`, `--credits`, read by one parser, `trekArgs_parse`), plus `--help` and `--version`. Scans are styled with glyphs and colour on a colour terminal, plain when piped, with `NO_COLOR`, or with `--classic`.

| A saved game on file
| The original wrote `trek.dump` in the current directory; the port keeps the save in a slot (`TrekDump`). The session's slot lives as long as the session; the CLI's is a file at `$XDG_STATE_HOME/bsd-trek/trek.dump` (`~/.local/state` on Linux, `~/Library/Application Support` on macOS, `%LOCALAPPDATA%` on Windows), so a save outlives the process. The engine does not change.

| Version `0.1.0`
| The gameplay is complete, but the engine's exports widened once for the bridge (`state_show`, `TrekState`). `1.0.0` comes once the ARGUS bridge has used the engine.

| Credits in the game and on the command line
| `credits` at the `Command:` prompt and `trek --credits` show one text (`TREK_CREDITS`): the game's authors as the C's own credits name them, the port and its author, and a word on mise and ChRIS. The command is the port's, added last to the C's command table, so `?` lists the C's own first, no recorded game changes, and it takes no time (no stardate passes, the Klingons do not act).

| Ctrl-C ends the game
| As the C's default interrupt did: at once, with no save and status 130, and no trace from readline. `dump` saves first.

| A README for the player
| The game first: play in one line, how to play, options, saves, history and credit, licence; mise last. It carries one disclaimer: Star Trek is Paramount's trademark, and this is an unaffiliated port of a 1976 game. The package holds no Paramount art or sounds.
|===

=== The boundary

`npm run lint:trek` (`scripts/trek-isolation.mjs`, in CI) fails when a source file in `packages/trek` imports anything but its own modules, Node's, `../package.json` (for `--version`), and the dependencies its `package.json` names, or when that `package.json` names anything of `@fnndsc`. A convention alone is how brasa's builtin came to reach into the session's question and sink; the lint keeps the boundary from eroding one convenient import at a time.

=== Fidelity

The port reads side by side with the C. A function ported from the C keeps the C's name (`dowarp`, `getcodpar`, `klmove`), as do the game state's fields (`Ship.shldup`, `Now.klings`) and the stand-ins for C library calls (`printf`, `getchar`, `srandom`); its JSDoc names the C function and file it came from (`C: \`dowarp()\` in warp.c.`), the C's own comments are kept in its authors' words, and each module's header names the NetBSD C file and revision. Everything the port added is named in the house style, `object_verb`: the command (`cli_run`, `dumpPath_get`), the engine's entry (`trek_play`, `trekArgs_parse`), the terminal a host implements (`TrekTerminal`: `text_write`, `question_ask`, `seconds_sleep`), the styled scans, snapshots and helpers. `lint:trek` holds the line: a name that is not `object_verb` passes only when its JSDoc names it as the C's. The whole package is typed explicitly, with named interfaces for its non-primitive data and a JSDoc block on every function.

The tests replay eighteen games recorded from the C built with glibc's `random()`: for the same seed and answers the port prints the C's transcript byte for byte. The same games replay through the `trek` command itself, input piped in, with the same result.

=== Publishing

npm's trusted publishing cannot create a package name, so the first version is published by hand:

. The PR that adds the package is built; it is not merged yet.
. The operator publishes `0.1.0` by hand from pannotia (npm user `debio`), from the branch with `dist` built.
. The operator configures the trusted publisher on npmjs: FNNDSC / mise / `release.yml` / no environment / "Allow npm publish" ticked.
. The release is verified with a clean `npx bsd-trek` in an empty directory, not `npm view`: a version record proves nothing about installing.
. The PR merges, and brasa releases depending on `bsd-trek`. Later versions release through changesets with their siblings.

== The engine shows its state

The engine asks every question through the C's own `getpar` functions, and a host answers them one line at a time; that does not change. What a host that draws the game needs is the state, not the printed scans: `TrekTerminal` has an optional `state_show(state)`, called with a deep copy of the whole `TrekState` before each `Command:` prompt. The recorded C games replay unchanged (nothing is printed for it), a terminal that only prints leaves it out, and `TrekState` and its parts are exported. This is the one widening of the terminal the bridge needed; the typed asks once planned here are not: the bridge sends the commands itself, so it knows what it asked.

The session's `trek` passes the state on as a typed event, `games.trek.state`, through a channel that did not exist before and is now part of mise's contract: `OutputSink.event_write(kind, data)`, the `event` message from the daemon to the command's origin surface (live only, like output), and `event_receive` on the ARGUS client. A surface shows the kinds it knows and drops the rest.

== The ARGUS bridge

Running `trek` in ARGUS takes the whole screen, and ARGUS comes back when the game ends. Mockups: https://claude.ai/artifact/MojBJ5btnJEchTenGCBkAf[the trek canvas]; v4 is this design (the BRIDGE view and the four station views); v1 to v3 are what came before (private to the operator until shared).

=== The harness plays the game

The bridge is a player at a terminal, not a rewrite of the game. It runs the session's `trek` as the operator's own command, reads the state the engine shows before every `Command:` prompt, and answers the engine's questions one at a time with lines built from its controls: pressing MOVE sends `m`, the course wheel's SET COURSE answers `Course:`, the distance slider's ENGAGE answers `Distance:`. The engine asks only what it would ask a typist, so the bridge never predicts the dialogue; it answers the prompt in front of it, identified by its text and the station that is open. Questions the engine asks on its own ("Are you sure that is wise", "Do you want a burst", Spock's "Shall we cancel our rest period", "Another game") are a yes/no strip over the body. Nobody types: the ship's log at the foot of the screen is the game's own prose, read-only, in the bridge's type (the C's tables, status report, damage report, score, scans, are panes drawn from the state, not log text). Ranges live in the bridge as presentation (a course is 0 to 360, a warp factor 1 to 10, phaser units up to the energy the state shows); the engine still checks every answer, so the bridge can never do more than a typist could.

=== Why a takeover, not a pane

* It is the shell's own idiom. In a terminal a full-screen program (`vi`, `tetris`) switches to the alternate screen and hands it back on exit; ARGUS, built around an embedded terminal, does the same one level up.
* A pane among panes would mislead. While the game runs it is the session's running command and holds the lane; anything another pane asks the session queues behind it. A screen given wholly to the game says so.
* ARGUS's zoom already removes its gutter, header and console; a takeover is a zoomed surface opened when the game starts and closed when it ends, with the frame drawn by the bridge itself (two elbows: the header's bar sweeping into the upper gutter, the body's into the stations).

=== The screen

* *The header* carries the ship's state, every value one that play changes: condition (and why), ship (energy, shields, torpedoes), mission (stardate, time left, Klingons), position and score, and what changed since the last command (a diff of two states). It is the C's status report, always on.
* *The gutter* is trek's own: its block, then the views, BRIDGE, HELM, TACTICAL, ENGINEERING, COMPUTER, and LEAVE BRIDGE. A view changes what the body shows, as an LCARS gutter does; a command works in place and never jumps the view.
* *BRIDGE* shows everything at once: the long-range scan and the galaxy chart (only what the ship has seen) on the left, the chart sized to the room, engineering in its own view; the short-range scan and the ship's commands in the middle; HELM over TACTICAL on the right, each with its own commands and its own controls. The other views enlarge one station: HELM a big course wheel and long sliders; TACTICAL the wheel with Klingons at their bearings and the burst as a wedge, phasers and shields beneath; ENGINEERING the damage report whole (repair times in flight and docked, as `dcrept` prints them) and the ship's reserves; COMPUTER the chart large and the computer's requests as pills, with the answers drawn.
* *The controls follow the value, one per value, lit by the command.* A course wheel (0 to 360, Klingons and starbases at their bearings; a sector pressed on the scan fills course and distance); sliders for continuous values (distance 0 to 15, warp factor 1 to 10 with the warning above 6, rest time up to the time left, phaser units up to the energy free, spread 0 to 1); pills for choices (manual or automatic, up or down, burst angle, yes or no). A dimmed control is a readout: the warp factor slider sits at the ship's speed until WARP lights it. In trek(6) shields are up or down and their energy a readout refilled at a starbase; there is no transfer to set.
* *LEAVE BRIDGE* abandons the question the engine is waiting on; the engine reads end of input and ends the game as the C does, and ARGUS returns. Esc asks first.

=== Sound

Every sound is synthesized in the browser; no recording ships. Each cue is a spectral resynthesis of a reference recording (hundreds of partial tracks, each with its own pitch and amplitude curve, plus the residual as shaped noise), kept as a compact table and played by Web Audio oscillators and band-pass noise. The bank: the console's own voice (press, acknowledge, deny, view open and close, the computer working, a sensor sweep, the scanner) and the bridge's (ship phasers, photon torpedo, incoming fire, hull hit, explosion, red, yellow and green alert, dock, warp, impulse, transporter, self-destruct, hail, game over). Pills that only open, set or answer take one computer beep each from a pool of 77; pills that do something are heard as the thing (FIRE is the phaser or the torpedo, ENGAGE is warp or impulse) and never beep. Events read from the state and the log decide the rest: condition changes, a Klingon firing, a hit, a kill, docking, the hail, abandon, destruct, the end. ARGUS's existing beeps (press, arrive, retreat) are played by the same engine, and the porter's `PORTER_SOUNDS_DIR` override stays. The audio pill is the one mute. The bank was chosen on https://claude.ai/artifact/VwZqrUrQAn2zsdXf7Np6bu[the sound chooser] (private to the operator); the choices and the analysis that makes a model from a clip live in `tools/trek-sound`, the models and `bank.json` under `apps/argus/public/sound/`.

The frame's four beeps (press, arrive, retreat, refuse) go through the same voice. A deployment that keeps recordings of its own (`PORTER_SOUNDS_DIR`) still hears them: the porter names the files its folder holds at `sounds/index.json`, the page plays those as recordings and synthesizes the rest. The game's events are heard from what the engine says and shows: the alerts, docking and a new quadrant's sensors from the state; an attack, a hit, a kill, a torpedo's track, a phaser bank firing, a starbase answering and the self-destruct from the engine's own lines, so one kill is one explosion; ENGAGE as warp or impulse when the distance is answered; ABANDON, DESTRUCT and COMPUTER as the transporter, the signal and the computer thinking. A cue asked for in the same instant as another plays a little after it.

=== Settled

* Esc asks "Leave the bridge? The game ends"; LEAVE BRIDGE leaves. Abandoning the engine's open question is end of input, as Ctrl-D is: the game ends as the C does, and the console's outcome is the game's own.
* The bridge opens from `trek` on the command line of either console (the ARGUS language's `trek` subject: prefix-`:` or the LANG capsule, then `trek [--seed <n>]`), and from `trek` typed at the transcript console (ARGUS claims the line before it reaches the wire, then runs the command itself). In a terminal console the bare line typed at the prompt runs in that chell and plays as text, as it does in any terminal. The surface claims only a game: `trek --credits`, `--help` and `--version` answer at once in the session.
* The bridge wears ARGUS's theme: its palette tokens, under whichever scheme is set.
* A command works in place; only the gutter changes the view.
* "A program may take the screen and give it back" is a surface decision: its laws and a row in `apps/argus/docs/aegis.adoc` land with the takeover.
* A distance is in quadrants, as the C reads it: a sector pressed on the scan sets a tenth per sector, and the helm's note says where the ship arrives and what the move costs, worked out as the computer would.
* The computer's requests are pills on the COMPUTER view (and on the BRIDGE view's strip). A request pill at `Command:` sends `c` and answers `Request:` itself; the questions a request then asks (a target's quadrant and sector, a range, a distance and warp factor) are answered from the view's panels, which are the controls: the course panel aims at a quadrant pressed on the chart and a sector pressed on a scan, the cost panel's sliders hold the distance and warp factor. The panels also show the arithmetic live, mirrored from the C (`kalc`, `warpcost`, `impcost`, `pheff`, `score`), and the engine's own answer is drawn beside them; the engine's print is the authority, and the mirrors are tested against it.
* Manual phasers are played at TACTICAL: each bank's units, course and spread from the slider, wheel and slider in turn, and FIRE THE BANKS SET sends the bank of 0 units that ends the banks, as the C reads it.
* A station's head shows the step the command is on and a CANCEL pill whenever the open question has a "never mind" in the C (a course of -1, a rest of 0).
* The C's device table runs past its last device with two `*ERR*` rows; the bridge lists the fourteen devices.

=== Marks and motion (epic #1172)

The second round, grilled on a mockup page and settled 2026-10-19. One rule: nothing on the screen moves without an engine line or a state change behind it. A torpedo follows the printed track; a Klingon flies the sectors its `moves to` line names; a move joins the readout before to the readout after along the committed course; a kill bursts when its line arrives. The one motion with no line behind it is the stars breathing.

* *Marks, not letters.* The short-range scan is one picture: each sector a pressable cell (`role=button`, walked by the arrow keys, Enter presses) carrying a symbol for what it holds. The C's glyphs stay in titles, the legend and the log, the engine's own voice. One symbol table feeds the scan, the wheels' rims, the target pills and the legend, so one mark means one thing everywhere. The symbols are abstract: a saucer over a hull, a spindle station, a banded planet, an eight-ray star, a spiral; no franchise hull.
* *Four Klingon marks.* The engine's Klingon list has no ids. A Klingon takes the least-worn of four marks when first seen at a sector; the engine's own lines carry it (`Klingon at x,y moves to a,b`, `escapes to quadrant`, `destroyed`); a kill frees it. With the short-range sensors damaged the engine prints no such lines, and the marks follow list order. A Klingon faces the ship, from the bearing in the state.
* *The ship's mark turns* to the course the moment SET COURSE commits it, and keeps its heading after the move.
* *The shield ring* around the ship has the width and colour of the shield over its maximum, read from the state: thick and cool when full, warmer and thinner as it drains, thin and dashed when down, the starbase's own when docked. A `HIT` line flares it and takes the absorbed share off it (hit × absorb% ÷ max, the engine's own arithmetic).
* *Charts.* An unscanned quadrant is an empty cell; a supernova (the C's `///`, a dead quadrant) wears the radiation trefoil; the long-range scan shows the edge of the galaxy as such, where the C prints `*`.
* *Standing order.* The harness sends the engine's own `l` at the first `Command:` prompt and whenever the ship arrives in a new quadrant, while the long-range sensors work. It is a command, not a pill: nothing is heard for it, and its lines go in the log folded under one dim head. Not every turn: between arrivals the codes keep themselves, because `klmove` raises the quadrant a Klingon flees to.
* *Motion (S6).* The frame queue is the clock: lines replay in order, each frame and its cue start together, the log scrolls with the picture; Esc, a view pill or a command pill jumps to the final state, and reduced motion always does. Torpedo 140 ms per printed point, ship and Klingon 170 ms per sector, bursts 800 ms. A move lays a dashed track from the readout before to the readout after along the committed course, a pulse runs it as the orrery's tubes carry theirs, the ship slides with it; a crossing runs the ship off the edge, dims and rescans the grid, blooms the long-range cell that becomes HERE, and runs it in from the matching edge; an obstacle stop ends where the state says. A Klingon flies its line on a red track. A phaser beam joins the two named sectors; a Klingon's beam reaches the ship, and none is drawn when the HIT line has no `from`. Bursts after the ARGUS node flare: a kill, a nova (twelve spikes, star colour), a misfire (red, short). The photon torpedo is an orange-red sphere with a white heart and ten flickering pulses, trailing a comet tail that fades, in its own colour under every palette. Four cues join the bank: `nova`, `supernova`, `klingon-pass`, `shield`.
* *Proof (S7).* Two laws: `a-mark-means-one-thing-everywhere` (lint: one symbol table feeds the grid, the wheels, the targets and the legend) and `a-frame-replays-a-printed-line` (smoke on seed 13: a torpedo at course 6, the track's frames equal to the printed points, the burst after the kill line, no frame without a line, the long-range panel filled at the first prompt).

== The order of work

. *S1, the package* (#1156, done): `packages/trek` with the engine, the `trek` command, its README and licence, `lint:trek`; brasa's builtin as a consumer; this document. Merged after the first publish by hand.
. *S2, the engine shows its state* (#1163): `state_show`, the `event` channel through menu, brasa, calypso and the ARGUS client; the session's `trek` sends `games.trek.state`.
. *S3a, the takeover and the BRIDGE view* (#1164): ARGUS's takeover layer and the harness, header, scans, helm and tactical, the ship's log, LEAVE BRIDGE; entry from the GAMES pane and the console line.
. *S3b, the station views* (#1165): HELM and TACTICAL large with the scan beside them, ENGINEERING with the damage control report whole (repair times in flight and docked) and the ship's reserves, COMPUTER with the chart large and the requests as pills with the answers drawn; manual phasers; the score in the header; the frame's two elbows joined.
. *S3c, sound* (#1167): the resynthesis player (`apps/argus/src/lcars/synth.ts`), the bank as static files under `sound/`, the cues on their events and a beep per pill, ARGUS's own beeps through the same voice with the porter's recordings kept where it has them, the audio pill the one mute; the analysis tooling in `tools/trek-sound`.
. *S4, proof* (#1168): the `trek-bridge` smoke scenario (the transcript lane's), and four AEGIS laws: a program may take the screen, a program gives the screen back, a bridge answers the prompt in front of it, a pill that acts is heard as the thing.
. *S5, marks* (epic #1172): the scan as one picture with marks for letters, the four Klingon marks carried by the engine's lines, the ship's heading and shield ring, the legend, the charts' empty and dead quadrants, the long-range standing order.
. *S6, motion* (epic #1172): the frame queue, the move's track and pulse, the crossing, Klingon flight, beams and bursts, the photon torpedo, four cues.
. *S7, proof* (epic #1172): the laws and the seed-13 smoke scenario.

== Deferred, deliberately

These wait for a second consumer or a first outside contributor; designed now, they would take the shape of nothing in particular.

* *A browser build*: ARGUS trek playable on a static page with no daemon, the kernel in a worker over an in-memory store. It needs an audit of what brasa's core takes from Node.
* *A persistent memory backend*: the null backend (`nullBackend_make`) is already a filesystem held in memory, and enough for a first `--web` entry; saves and high scores would want it kept on disk or in browser storage, and a name better than "null".
* *Runtime loading of extensions*: an operator naming outside packages to load into the kernel and ARGUS, with the trust that implies.
* *A neutral org* for the framework and community extensions, apart from FNNDSC's ChRIS backend.
* *Splitting brasa's core from its ChRIS backend* into separate packages, so a bridge install no longer downloads the CUBE client stack it never loads.
